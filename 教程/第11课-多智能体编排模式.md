## 11.1 四种编排模式:多 Agent 系统的"组织结构图"

单个 Agent 回答"怎么把一件事做好",编排(orchestration)回答"几件事怎么分工"。常见的编排模式有四种。

### 模式一:串行流水线(Pipeline)

```
输入 → Agent A → Agent B → Agent C → 输出
```

每一步消费上一步的输出。特点:**延迟是各步之和**(T1+T2+T3),**失败会级联**——上游输出错了,下游拿着错的输入继续"一本正经"。适用场景:任务天然分阶段、每一步真的依赖上一步的全部输出(如"翻译→润色→审校")。

### 模式二:并行扇出 + 汇总(Fan-out / Fan-in)

```
        ┌→ Agent A(查景点) ┐
输入 ───┼→ Agent B(查天气) ┼──→ 汇总 Agent(整合)
        └→ Agent C(查酒店) ┘
```

多路任务互不依赖,同时执行;最后由一个汇总环节整合。特点:**延迟 ≈ max(各路) + 汇总**,一路失败不会污染其他路的输出。适用场景:多视角的独立信息收集——这正是你项目前三步的样子(11.3 节验证)。

### 模式三:路由分发(Router)

```
        ┌→ Agent A(退款问题)
输入 → 路由器 ┼→ Agent B(物流问题)
        └→ Agent C(投诉)
```

先由一个分类器(LLM 或规则)判断输入类型,把请求分发给专门的处理者,通常只走一条支路。适用场景:输入类型多样、每类有专属处理逻辑(客服分流是原型)。失败传播的特殊性:**路由错了,后面全错**,而且错误离源头最远、最难排查。

### 模式四:协作讨论(Debate / Collaboration)

```
Agent A ⇄ Agent B ⇄ Agent C   (多轮互看输出、互相批评、迭代修正)
```

多个 Agent 不是流水线,而是"圆桌":各自生成,互看草稿,多轮修订后收敛。适用场景:答案有客观对错、值得多视角校验的开放式任务(方案评审、代码审查)。代价:轮数不固定、token 成本最高、不保证收敛。

### 选型速查表

| 模式 | 延迟 | 失败传播 | 判断问题:该用它吗? |
|---|---|---|---|
| 串行流水线 | 各步之和 | 级联,上游错下游全错 | 下一步真的需要上一步的**全部**输出吗? |
| 并行扇出 | max(各路)+ 汇总 | 单路失败只影响汇总 | 这些任务真的互不依赖吗? |
| 路由分发 | 判别 + 单路 | 路由错误最难排查 | 分类标准清晰且稳定吗? |
| 协作讨论 | 最高 | 互相污染 | 结果值得多轮成本去校验吗? |

Anthropic《Building Effective Agents》(第 1 课引过)的原则同样适用于编排:**从最简单的模式开始,只在确有需要时增加复杂度。** 四种模式没有高下之分,只有匹配与否。

## 11.2 失败传播:编排设计中被忽视的半边

编排图画的是"正常路径";工程上一半的难度在"失败路径"。

- **串行流水线:** 最危险的是**静默级联**——上游不报错、只返回空或错,下游照样往下传,直到最后一环产出一份"看起来完整"的垃圾。
- **并行扇出:** 天然隔离,但**汇总点必须回答"部分失败怎么办"**:等所有路?跳过失败的路?整体失败?
- **协作讨论:** 一个固执的错误观点可能把整桌人带偏。
- **路由分发:** 误判一次,后面全部白干。

### 在你的项目里观察"静默失败"

问一个尖锐的问题:如果天气 Agent 的 `run()` 返回了空字符串(工具调用失败但没抛异常),`plan_trip` 会报错吗?

看 `backend/app/agents/trip_planner_agent.py` 的 248–252 行:

```python
# 步骤2: 天气查询Agent查询天气
print("🌤️  步骤2: 查询天气...")
weather_query = f"请查询{request.city}的天气信息"
weather_response = self.weather_agent.run(weather_query)
print(f"天气查询结果: {weather_response[:200]}...\n")
```

`run()` 返回什么,代码就照单全收。空字符串会被原样拼进第 262 行的 `_build_planner_query`,规划 Agent 拿到一段空的"天气信息",**凭想象编天气继续干活**——全程无异常、无日志告警。这就是静默级联的活标本。

还有一个更外层的机制要看:`plan_trip` 从 233 行开始一整个大 `try`,任何一步抛异常,都会跳到 275–279 行的 `except`——

```python
except Exception as e:
    print(f"❌ 生成旅行计划失败: {str(e)}")
    import traceback
    traceback.print_exc()
    return self._create_fallback_plan(request)
```

无论哪一步、以什么方式失败,最终都变成 `_create_fallback_plan` 编出的一份假行程。这个方法干了什么、为什么危险,是**第 14 课**的主角,本课先按下不表。

失败传播的三个对策,课程里会依次落地:**隔离**(本课实验里用 `return_exceptions=True`)、**诚实的降级**(第 14 课)、**超时与重试**(第 17 课)。

## 11.3 精读 plan_trip:被写成全串行的"并行扇出"

打开 `backend/app/agents/trip_planner_agent.py`,`plan_trip` 方法在 223–279 行,核心四步在 242–264 行:

```python
# 步骤1: 景点搜索Agent搜索景点                    # ← 242 行
print("📍 步骤1: 搜索景点...")
attraction_query = self._build_attraction_query(request)     # 244 行
attraction_response = self.attraction_agent.run(attraction_query)  # 245 行

# 步骤2: 天气查询Agent查询天气                    # ← 248 行
...
weather_response = self.weather_agent.run(weather_query)     # 251 行

# 步骤3: 酒店推荐Agent搜索酒店                    # ← 254 行
...
hotel_response = self.hotel_agent.run(hotel_query)           # 257 行

# 步骤4: 行程规划Agent整合信息生成计划              # ← 260 行
planner_query = self._build_planner_query(request, attraction_response, weather_response, hotel_response)  # 262 行
planner_response = self.planner_agent.run(planner_query)     # 263 行
```

现在做**依赖分析**——逐个步骤问:"它的输入从哪来?"

| 步骤 | 行号 | 输入依赖 | 只依赖 request? |
|---|---|---|---|
| 1. 景点搜索 | 242–246 | `_build_attraction_query(request)`(281–292 行) | **是** |
| 2. 天气查询 | 248–252 | 只用 `request.city` | **是** |
| 3. 酒店搜索 | 254–258 | 只用 `request.city` / `request.accommodation` | **是** |
| 4. 行程规划 | 260–264 | **前三步的全部输出**(262 行实参) | 否,必须等 |

结论一目了然:**真实依赖结构是"三路并行扇出 + 一步串行汇总"**。前三个 Agent 互相之间没有任何数据交换(回忆第 1 课架构图里"三箭头汇入规划 Agent"),完全可以同时执行;只有第 4 步必须等齐。

但代码按 1→2→3→4 书写并顺序执行,所以现在的端到端延迟是:

```
现状:T1 + T2 + T3 + T4
理想:max(T1, T2, T3) + T4
```

别忘了第 7 课的事实:一次 `run()` 内部可能有多轮"LLM 输出 → 执行 MCP 工具 → 结果回填 → 再请求 LLM"的循环。所以 T1、T2、T3 都是**几十秒级**,串行的浪费是真实的分钟级。这不是"代码风格问题",是用户等待时间的问题——前端 `api.ts` 第 8 行设了 2 分钟超时,慢就是在把用户往超时失败上推。

### 一个并行前必须正视的问题:共享资源

三个 Agent 共享同一个 `self.amap_tool`(168–175 行创建一次)和同一个 `self.llm`(164 行)。并行执行时它们会不会打架?——**框架源码不在本仓库,我不会替你编造答案**;但本课 11.5 节的步骤 4 会教你两件事:如何定位框架源码自行查证,以及如何用行为实验验证"结果有没有串台"。严肃对待这个问题:工具结果串台会让行程数据张冠李戴,比慢更糟。

## 11.4 先想清楚:gather 一个同步函数,会发生什么?

第 4 课你学过:`asyncio.gather` 调度**协程**。现在看新手必踩的坑。假设你直接写:

```python
# ❌ 错误示范:直接把同步调用塞进 gather
results = await asyncio.gather(
    self.attraction_agent.run(q1),   # 注意:这里是函数"调用"
    self.weather_agent.run(q2),
    self.hotel_agent.run(q3),
)
```

执行顺序是这样的:Python 先**从左到右求值三个实参**——三个 `run()` 在 `gather` 还没开跑之前就已经串行执行完了,一分钟都没省;它们各自返回一个普通字符串;然后 `gather` 收到三个字符串,发现它们既不是协程也不是 Future,直接抛 `TypeError`。最糟糕的组合拳:**时间一分没省,还搭一个报错**。这个坑你会在 11.5 的步骤 2 亲手踩一遍。

### 正确姿势:asyncio.to_thread 桥接

`asyncio.to_thread`(Python 3.9+)把同步函数扔进**线程池**执行:事件循环把"调用 `run(q1)`"这个动作交给某个工作线程,自己立刻拿到一个可等待的协程继续干活。三个这样的协程被 `gather` 同时调度,三个线程各自阻塞等待 LLM 的网络响应——**等待时间重叠了**。

```python
# ✅ 正确示范:函数本体作第一个参数,函数参数跟在后面
r1, r2, r3 = await asyncio.gather(
    asyncio.to_thread(self.attraction_agent.run, q1),
    asyncio.to_thread(self.weather_agent.run, q2),
    asyncio.to_thread(self.hotel_agent.run, q3),
)
```

两个细节:

- 参数传递方式:`asyncio.to_thread(fn, arg)` 而不是 `asyncio.to_thread(fn(arg))`——后者又变回了"先调用、再传结果",坑就白踩了;
- 为什么线程在这里有效、GIL 不碍事:GIL 只限制**同一时刻只有一个线程执行 Python 字节码**;线程在等待网络 I/O 时会释放 GIL。LLM 调用是 HTTP 请求,MCP 工具读子进程输出是 stdio I/O——全是等待,不是计算。第 4 课"协程 vs 线程 vs 进程"的结论在这里正式落地。

### 那"彻底异步化"呢?

理论最优解是把 LLM 调用换成原生异步实现(如 `httpx.AsyncClient` 或 OpenAI SDK 的异步客户端),连线程都省了。但 `SimpleAgent` 来自 hello-agents 框架(第 5 课),框架不提供异步 `run()`。你的选择:

- **改框架源码:** 侵入性强,框架一升级就失效,不建议;
- **to_thread 桥接:** 不动框架,拿到绝大部分收益(本项目的瓶颈是 I/O 等待)。

本课程取后者。什么时候值得为某个环节做原生异步化,第 12 课给出一棵完整的决策树。

## 11.5 动手实验:三路并行化与耗时测量

贯穿课程的原则:先观察、再动手、用数据说话。本课的改造只发生在**脚本层**,**不接进 FastAPI 路由**——路由那一层有自己的坑,第 12 课专门讲,提前接进去会把两件事搅在一起。

### 步骤 1:建立基线(改造前测 2 次)

新建 `backend/bench_parallel.py`:

```python
"""并行化改造前后计时
用法(cd backend 后):
  python bench_parallel.py serial     # 原版串行基线
  python bench_parallel.py parallel   # 第 11 课并行版
"""
import asyncio
import sys
import time

from app.agents.trip_planner_agent import get_trip_planner_agent
from app.models.schemas import TripRequest

REQUEST = TripRequest(
    city="北京",
    start_date="2026-10-01",
    end_date="2026-10-01",
    travel_days=1,               # 天数控 1,控制成本(仍要跑 4 个 Agent)
    transportation="公共交通",
    accommodation="经济型酒店",
    preferences=["历史文化"],
    free_text_input="",
)


async def plan_trip_parallel(agent, request):
    """第 11 课改造:三路 to_thread + gather,第 4 步保持串行汇总"""
    # 三条查询与 plan_trip 244/250/256 行完全一致
    attraction_query = agent._build_attraction_query(request)
    weather_query = f"请查询{request.city}的天气信息"
    hotel_query = f"请搜索{request.city}的{request.accommodation}酒店"

    t0 = time.perf_counter()
    attraction_response, weather_response, hotel_response = await asyncio.gather(
        asyncio.to_thread(agent.attraction_agent.run, attraction_query),
        asyncio.to_thread(agent.weather_agent.run, weather_query),
        asyncio.to_thread(agent.hotel_agent.run, hotel_query),
    )
    t1 = time.perf_counter()
    print(f"[计时] 前三路并行耗时: {t1 - t0:.1f}s")

    planner_query = agent._build_planner_query(
        request, attraction_response, weather_response, hotel_response
    )
    planner_response = await asyncio.to_thread(agent.planner_agent.run, planner_query)
    t2 = time.perf_counter()
    print(f"[计时] 第 4 步汇总耗时: {t2 - t1:.1f}s")

    return agent._parse_response(planner_response, request)


if __name__ == "__main__":
    mode = sys.argv[1] if len(sys.argv) > 1 else "serial"
    agent = get_trip_planner_agent()
    t_start = time.perf_counter()
    if mode == "serial":
        plan = agent.plan_trip(REQUEST)            # 原版(223–279 行)
    else:
        plan = asyncio.run(plan_trip_parallel(agent, REQUEST))
    total = time.perf_counter() - t_start
    print(f"[计时] {mode} 端到端总耗时: {total:.1f}s,城市: {plan.city}")
```

注意:**先预热跑一次再计数**——第一次请求包含 uvx 拉起 amap-mcp-server 子进程、LLM 客户端初始化,不属于被测对象。然后 `serial` 模式跑 2 次,记录总耗时。

### 步骤 2:亲手踩一遍"假并行"的坑(必做)

### 常见卡点

- **Q:并行版报 LLM 429 / 限流错误?** 三路同时打 API,瞬时压力 ×3,更容易触发供应商限流。先串行重试一次确认;系统性的退避重试是第 17 课内容,本课先记录现象。
- **Q:并行后耗时几乎没变?** 三查:是否真的用了 `to_thread`(而不是先调用再传结果);三路里是否有一路特别慢(看 `[计时]` 输出,max 由它决定);单次测量有噪声(每次 `run()` 内部的工具调用轮数可能不同)——这正是要测 2 次的原因。
- **Q:控制台 print 交错、日志看不清?** 这是并行的正常现象,不是 bug;日志系统化治理在第 19 课(loguru)。
