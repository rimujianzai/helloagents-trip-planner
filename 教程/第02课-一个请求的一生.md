## 1.1 全景:一次请求的八站

先把全程浓缩成一张表。每一站本课都会停下来精读,你可以把这张表当成行军路线:

| # | 站点 | 位置 | 进站数据 | 出站数据 |
|---|---|---|---|---|
| 1 | 用户填表、点击提交 | `Home.vue:251` `handleSubmit` | 表单状态(日期是 Dayjs 对象) | 普通对象 `TripFormData`(`Home.vue:280-289`) |

## 1.2 第一站:前端表单(Home.vue)

打开 `frontend/src/views/Home.vue`(654 行)。用户看到的表单由三个分区组成:目的地与日期、偏好设置、额外要求(模板 25–200 行),对应的状态定义在脚本区:

```ts
// Home.vue:224-233
const formData = reactive<TripFormState>({
  city: '',
  start_date: null,      // 注意:此时还是 Dayjs 对象,不是字符串
  end_date: null,
  travel_days: 1,
  // ... transportation / accommodation / preferences / free_text_input
})
```

有一个容易被忽略的细节:日期选择器绑定的值是 **Dayjs 对象**(见 219–222 行的类型定义),不是字符串。用户改日期时,`watch`(236–249 行)自动算出天数——`end.diff(start, 'day') + 1`,超过 30 天直接拦下。这和后端 `schemas.py:15` 的 `travel_days: int = Field(..., ge=1, le=30)` 是**前后端双重校验**:前端为了体验,后端为了安全。

真正发出请求的是 `handleSubmit`(`Home.vue:251-320`):

```ts
// Home.vue:280-291(节选)
const requestData: TripFormData = {
  city: formData.city,
  start_date: formData.start_date.format('YYYY-MM-DD'),   // Dayjs → 字符串!
  end_date: formData.end_date.format('YYYY-MM-DD'),
  // ... travel_days / transportation / accommodation / preferences / free_text_input
}

const response = await generateTripPlan(requestData)
```

**数据形态变化第 1 次:Dayjs 对象 → `"2025-06-01"` 字符串。** 这是数据离开前端前的最后一次"本地变形"。

顺带看一眼 262–277 行:请求期间的进度条是 `setInterval` 每 500 ms 加 10% 的**假进度**,状态文案("正在搜索景点…")也是按时间切换的,和后端真实进度毫无关系。真实进度要等第 26 课的 SSE 流式输出——现在记住"这是装的"即可。

## 1.3 第二站:Axios 与类型契约(api.ts)

`frontend/src/services/api.ts` 只有 65 行,是前端**所有**后端请求的出口:

```ts
// api.ts:4-12
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8000'

const apiClient = axios.create({
  baseURL: API_BASE_URL,
  timeout: 120000, // 2分钟超时
  headers: {
    'Content-Type': 'application/json'
  }
})
```

三个值得记住的事实:

1. **`baseURL` 来自环境变量 `VITE_API_BASE_URL`,默认 `http://localhost:8000`**(第 4 行)。注意这是**绝对地址**——这个细节在第 3 课讲 CORS 与 Vite 代理时有关键作用。
2. **`timeout: 120000`**(第 8 行):2 分钟。为什么敢设这么长?因为一次规划要串行跑 4 次 LLM 往返,常常几十秒。等第 27 课做了流式输出,这个"2 分钟干等"就该退场了。
3. **两个拦截器**(15–36 行)统一打印请求与响应日志——本课实验就靠它。

请求本体在 43 行:

```ts
// api.ts:43-44
const response = await apiClient.post<TripPlanResponse>('/api/trip/plan', formData)
return response.data    // axios 已把响应体解析成对象,类型即 TripPlanResponse
```

响应的 TS 类型 `TripPlanResponse`(`types/index.ts:90-94`)与后端 Pydantic 模型(`schemas.py:153-157`)字段一一对应——但这是**手工维护的对应**,没有任何工具自动同步。改了后端模型忘了改 `types/index.ts`,TypeScript 不会提醒你。这个隐患第 23 课会系统处理。

## 1.4 第三站:FastAPI 接单(trip.py)

跨过了网络,请求落在 `backend/app/api/routes/trip.py`。先看路径是怎么拼出来的:

- `trip.py:11` — `router = APIRouter(prefix="/trip", ...)`
- `main.py:30` — `app.include_router(trip.router, prefix="/api")`

两层前缀相加,才是完整的 `POST /api/trip/plan`。

```python
# trip.py:20-52(节选)
async def plan_trip(request: TripRequest):
    try:
        print(f"\n{'='*60}")
        print(f"📥 收到旅行规划请求:")
        print(f"   城市: {request.city}")
        ...
        # 获取Agent实例
        agent = get_trip_planner_agent()          # 40 行

        # 生成旅行计划
        trip_plan = agent.plan_trip(request)      # 44 行

        return TripPlanResponse(                  # 48-52 行
            success=True,
            message="旅行计划生成成功",
            data=trip_plan
        )
```

这一站有三件事值得精读:

**① 参数校验发生在函数执行之前。** `request: TripRequest` 不是普通字典——FastAPI 会先把请求体 JSON 喂给 Pydantic,字段缺失、`travel_days` 超出 1–30、类型不对,都会直接返回 422 错误,你的函数体根本不会执行。第 3 课你会在 `/docs` 里亲手触发一次 422。

**② 40 行的 `get_trip_planner_agent()` 是单例**(定义在 `trip_planner_agent.py:422-429`):全局只在第一次调用时创建 `MultiAgentTripPlanner`,之后复用。这意味着**第一次请求会额外背负全部初始化成本**——包括拉起 `uvx amap-mcp-server` 子进程(168–175 行)。你的第一次规划格外慢,原因就在这里。

**③ 44 行是全项目最重要的"坑位坐标"**:`agent.plan_trip(request)` 是一个**同步方法**(`trip_planner_agent.py:223` 用的是 `def`),却被包在 `async def` 路由里直接调用。它执行期间,整个事件循环都被卡住——两个用户同时规划,第二个必须干等第一个跑完全部四步。第 4 课讲原理,第 12 课压测复现并修复。现在只需在架构图上把这个位置标红。

异常路径在 54–61 行:任何异常都被转成 `HTTPException(status_code=500)`,`detail` 里带着错误信息——前端 `api.ts:47` 读的就是这个 `detail`。

## 1.5 第四站:四步串行(trip_planner_agent.py)

进入项目的心脏 `MultiAgentTripPlanner.plan_trip`(223–279 行)。剥掉日志,核心就是 242–264 行的固定四步:

```python
# trip_planner_agent.py:242-264(节选;原注释标注了步骤序号)
attraction_query = self._build_attraction_query(request)
attraction_response = self.attraction_agent.run(attraction_query)      # 245 行:步骤1

weather_query = f"请查询{request.city}的天气信息"                       # 250 行
weather_response = self.weather_agent.run(weather_query)               # 251 行:步骤2

hotel_query = f"请搜索{request.city}的{request.accommodation}酒店"      # 256 行
hotel_response = self.hotel_agent.run(hotel_query)                     # 257 行:步骤3

planner_query = self._build_planner_query(request, attraction_response,
                                          weather_response, hotel_response)  # 262 行
planner_response = self.planner_agent.run(planner_query)               # 263 行:步骤4
```

**这一站的数据形态是全链路最"粗糙"的:每一步的输入和输出都是纯字符串。** LLM 响应字符串被原样存进变量,再原样拼进下一步的提示词——没有结构、没有字段。项目目前用字符串当 Agent 之间的"传送带",这正是第 13 课结构化输出要改造的对象。

三个步骤的 query 来源各有不同:

- **步骤 1** 来自 `_build_attraction_query`(281–292 行)。这里藏着两个已知问题:

```python
# trip_planner_agent.py:284-291(节选)
if request.preferences:
    # 只取第一个偏好作为关键词
    keywords = request.preferences[0]        # 286 行:多选偏好被静默丢弃!
else:
    keywords = "景点"

# 直接返回工具调用格式
query = f"请使用amap_maps_text_search工具搜索{request.city}的{keywords}相关景点。\n[TOOL_CALL:amap_maps_text_search:keywords={keywords},city={request.city}]"   # 291 行
```

  你在首页勾选"历史文化 + 美食"两个偏好,实际只有"历史文化"生效——**Bug 台账 +1**(第 21 课修复)。291 行把 `[TOOL_CALL:...]` 直接预写进用户消息,等于替 Agent 做了调用决定——第 1 课你已经见过它,第 7 课将拆解框架如何解析它,第 8 课将实验"去掉注入会怎样"。

- **步骤 2、3** 的 query 就是两行 f-string(250、256 行),没有任何注入。
- **步骤 4** 的 query 由 `_build_planner_query`(294–326 行)组装:基本信息 + 三个步骤的完整响应字符串全部拼进一条用户消息。这是第 6 课提示词工程的主战场,本课先记位置。

注意 246、252、258、264 行的日志只打印每个响应的**前 200(或 300)个字符**——后端控制台因此不是全量回放,做追踪实验时别被它误导。

## 1.6 第五站:从字符串到 TripPlan(_parse_response 与 schemas.py)

步骤 4 的响应仍然是一坨可能包含 JSON 的字符串。267 行调用 `_parse_response`(328–369 行)把它变成强类型:

```python
# trip_planner_agent.py:342-362(节选)
if "```json" in response:            # 策略1:markdown 围栏
    ...
elif "```" in response:              # 策略2:普通围栏
    ...
elif "{" in response and "}" in response:   # 策略3:裸找大括号
    ...
else:
    raise ValueError("响应中未找到JSON数据")

data = json.loads(json_str)          # 359 行
trip_plan = TripPlan(**data)         # 362 行:Pydantic 二次校验
```

三种提取策略依次尝试,全失败则走 `_create_fallback_plan`(371–415 行)——用**编造的假景点、假坐标**(393 行写死了北京附近的经纬度)拼一份计划。为什么说"编造假数据比报错更糟",这份 fallback 为什么要拆,第 14 课专门讨论;三种提取策略各自的漏洞,第 13 课逐个击破。

`TripPlan(**data)` 能"接管"的前提,是 `schemas.py` 把数据的形状定义得足够细。本课你只需要认识三个模型:

| 模型 | 位置 | 角色 |
|---|---|---|
| `TripRequest` | `schemas.py:10-33` | 入口契约:8 个字段的请求体 |
| `TripPlan` | `schemas.py:142-150` | 核心数据:`days` / `weather_info` / `budget` |
| `TripPlanResponse` | `schemas.py:153-157` | 出口包装:`success` / `message` / `data` |

再看一个"模型层兜底"的精彩例子:规划提示词要求"温度必须是纯数字"(trip_planner_agent.py:142),但 LLM 偶尔还是会输出 `"25°C"`,防线在模型层:

```python
# schemas.py:119-130
@field_validator('day_temp', 'night_temp', mode='before')
@classmethod
def parse_temperature(cls, v):
    """解析温度,移除°C等单位"""
    if isinstance(v, str):
        v = v.replace('°C', '').replace('℃', '').replace('°', '').strip()
        try:
            return int(v)
        except ValueError:
            return 0
    return v
```

提示词是第一道防线(尽量不犯错),Pydantic 校验器是第二道(犯错了能救回来)。**两层防线**的思想会在第 13 课升级成完整的重试机制。

## 1.7 第六站:回到前端

`TripPlan` 实例在 `trip.py:48-52` 被包进 `TripPlanResponse`,FastAPI 序列化成 JSON 发回。前端拿到后:

```ts
// Home.vue:297-306(节选)
if (response.success && response.data) {
  // 保存到sessionStorage
  sessionStorage.setItem('tripPlan', JSON.stringify(response.data))   // 299 行
  message.success('旅行计划生成成功!')
  setTimeout(() => {
    router.push('/result')                                            // 305 行
  }, 500)

```

**数据形态变化:`TripPlan` 对象 → JSON 字符串 → 存入 sessionStorage。** 为什么用 sessionStorage 而不是 props 或全局状态?因为发生了**页面级跳转**(router.push 到新路由),跨路由传大对象,存 storage 是最省事的办法;sessionStorage 的生命周期是"当前标签页",刷新不丢、关页即清。代价是类型完全失守(读出来是 `string`),第 24 课组件化改造时会重新设计这一段。

结果页 `Result.vue`(1391 行,全项目最大文件)在挂载时读回数据:

```ts
// Result.vue:329-339
onMounted(async () => {
  const data = sessionStorage.getItem('tripPlan')     // 330 行

    tripPlan.value = JSON.parse(data)                 // 332 行:JSON 字符串 → TS 对象

## 1.8 顺手抓第一个 Bug:/api/trip/health 必然 503

`trip.py` 里还有一个从未被认真跑过的接口——健康检查(64–85 行):

```python
# trip.py:69-85
async def health_check():
    """健康检查"""
    try:
        # 检查Agent是否可用
        agent = get_trip_planner_agent()      # 73 行

        return {
            "status": "healthy",
            "service": "trip-planner",
            "agent_name": agent.agent.name,             # 78 行
            "tools_count": len(agent.agent.list_tools()) # 79 行
        }
    except Exception as e:
        raise HTTPException(
            status_code=503,
            detail=f"服务不可用: {str(e)}"
        )
```

现在做一次代码走查,像第 21 课要教你的那样——**核对契约**:78–79 行访问的是 `agent.agent.name` 和 `agent.agent.list_tools()`。`agent` 这里是 `get_trip_planner_agent()` 返回的 `MultiAgentTripPlanner` 实例,它的属性有哪些?回到 `trip_planner_agent.py:158-215` 的 `__init__`:`llm`、`amap_tool`、`attraction_agent`、`weather_agent`、`hotel_agent`、`planner_agent`——**根本没有 `.agent` 这个属性**。

结论可以纯靠推理得出:`agent.agent` 抛 `AttributeError` → 被 81 行的 `except` 捕获 → 返回 503。**这个接口在任何情况下都不可能返回 200。** 如果环境已跑通,动手实测坐实它:`curl http://localhost:8000/api/trip/health`(或在 `/docs` 里点 Execute),必得 503。观察后端日志你还会发现一个滑稽的副作用:这次调用先**完整初始化了一遍多智能体系统**(73 行),然后才在 78 行摔倒——包括拉起 uvx 子进程。

为什么这个 Bug 能一直活着?看 `api.ts:54-62`:前端定义的 `healthCheck()` 调的是**根路径** `/health`(实现在 `main.py:80-87`,工作正常),从来没人调 `/api/trip/health`。**死代码里的 Bug 不会自己暴露——健康检查不健康,恰恰说明"写了没人测"比"没写"更危险。**

把发现记录下来。新建 `docs/bug-log.md`(本课程的 Bug 台账,第 21 课逐个清算):

```markdown
# Bug 台账

## BUG-001 /api/trip/health 必然 503
- 位置:backend/app/api/routes/trip.py:78-79
- 现象:GET /api/trip/health 永远返回 503,无论服务是否正常
- 原因:MultiAgentTripPlanner 没有 .agent 属性(实际属性见 __init__,158-215 行)
- 顺带发现:调用它还会触发一次完整的 Agent 初始化(73 行)
- 计划:第 21 课修复,并补测试

## BUG-002 多选偏好被丢弃
- 位置:backend/app/agents/trip_planner_agent.py:286
- 现象:preferences 只取 [0],勾选多个偏好时其余静默失效
- 计划:第 21 课修复
```

### 常见卡点

- **"第一次请求卡了很久,是不是坏了?"** —— 不是。单例懒加载(1.4 节事实 ②)让首次请求背负 uvx 冷启动 + 四次串行 LLM 往返。第二次请求明显变快,正好验证单例。
- **"埋点 print 没出现?"** —— 先确认后端是用 `--reload` 或重启方式跑的最新代码;再确认改的是后端正在用的那份文件;Windows 控制台中文/emoji 乱码不影响功能,`chcp 65001` 可解(第 3 课解释 start.bat 为什么第一行是它)。
- **"前端 Console 没有追踪日志?"** —— 确认请求真的从 `api.ts` 走(看 Network 面板里请求 URL 是否 `localhost:8000`),而不是被浏览器缓存或从别的入口发出。
