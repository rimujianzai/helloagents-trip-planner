## 20.1 什么值得测,什么必须 mock

不是所有代码都同等值得测。判断标准只有一条:**断言结果不依赖外部世界的代码,直接测;依赖外部世界的,把外部世界 mock 掉再测。**

把本项目代码过一遍筛子,得到一张清单:

| 代码 | 位置 | 类型 | 怎么测 |
|---|---|---|---|
| 三种 JSON 提取策略 | `_parse_response`(328–369 行)的提取分支 / `retry_parser.extract_json` | 纯函数 | 直接测,参数化喂样本 |
| 温度清洗校验器 | `schemas.py` 119–130 行 | 纯函数 | 直接测,参数化喂样本 |
| 重试解析循环 | `retry_parser.parse_with_retry` | 纯逻辑 + 注入的 `call_llm` | mock `call_llm` |
| 查询构造 | `_build_attraction_query`(281–292 行)、`_build_planner_query`(294–326 行) | 纯函数 | 直接测 |
| 编排流程 | `plan_trip`(223–279 行) | 胶水逻辑 | mock 四个 Agent 打桩 |
| LLM 调用 | 框架 `SimpleAgent.run` 内部 | 外部依赖 | **不测**(框架不在本仓库,且要花 token) |
| MCP 调用 | `MCPTool.run` → uvx 子进程 → 高德 | 外部依赖 | **不测**,service 层单测时 mock 掉 |
| Unsplash HTTP | `unsplash_service.py` | 外部依赖 | mock(第 17 课改造后同理) |

两条mock 原则,来自本项目踩过的坑:

1. **桩要"既像真的成功,也像真的失败"。** 第 11 课你验证过:天气 Agent 返回空字符串时 `plan_trip` 根本不报错——你的桩如果只会返回完美结果,就永远测不出这类问题。所以桩要覆盖"正常输出 / 空字符串 / 带围栏的 JSON"多种剧本。
2. **夹具用真实数据。** 第 13 课实验 B 的 `FIXTURES`(从真实日志粘出来的 Agent 输出)就是最好的测试样本来源——mock 数据离真实越近,测试的预言力越强。

## 20.2 装依赖、建目录:零测试到能跑 pytest

**第一步:开发期依赖独立成文件。** 生产部署不需要 pytest,所以别塞进 `requirements.txt`。新建 `backend/requirements-dev.txt`:

```
-r requirements.txt
pytest>=8.0.0
pytest-asyncio>=0.24.0
```

安装:`pip install -r requirements-dev.txt`(`-r` 表示同时装生产依赖)。另一种现代写法是 pyproject.toml 的 extras(`[project.optional-dependencies] dev = ["pytest>=8.0.0", ...]`,安装时 `pip install ".[dev]"`)——本仓库没有 pyproject.toml,先掌握 requirements-dev.txt 即可。`pytest-asyncio` 是给 `plan_trip_async`(第 11 课)这类协程测试用的;`TestClient` 所需的 httpx 主依赖里已有(`requirements.txt` 第 11 行)。

**第二步:目录组织。**

```
backend/
├── pytest.ini            # pytest 配置
├── requirements-dev.txt
├── app/...
└── tests/
    ├── conftest.py       # 共享 fixture
    ├── test_extract_json.py
    ├── test_schemas.py
    ├── test_retry_parser.py
    └── test_plan_trip.py
```

`pytest.ini`:

```ini
[pytest]
testpaths = tests
asyncio_mode = auto
```

`asyncio_mode = auto` 让 `async def` 测试自动被 pytest-asyncio 识别,不用逐个贴 `@pytest.mark.asyncio`。

**关键运行细节:必须从 `backend/` 目录运行 `pytest -v`。** 测试里的 import 写的是 `from app.agents...`,而 `app` 是 `backend/` 下的包——pytest 会把"当前工作目录"放进导入路径,站错了地方就是一屏 `ModuleNotFoundError`。

## 20.3 第一个单元测试:温度校验器(参数化)

最值得先测的是 `schemas.py` 119–130 行的温度清洗器——它只有 12 行,却是第 13 课"清洗"思想的范本,而且行为里藏着一个已知取舍(失败返回 0)。新建 `tests/test_schemas.py`:

```python
import pytest
from pydantic import ValidationError
from app.models.schemas import WeatherInfo


@pytest.mark.parametrize("raw,expected", [
    ("25°C", 25),      # 带度符
    ("25℃", 25),      # 全角度符
    (" 25 ", 25),      # 带空格
    ("25", 25),        # 数字字符串
    (25, 25),          # 本来就是 int
    (7, 7),            # 负数直接放行
    ("abc", 0),        # 清洗失败 → 0(第 13 课讨论过的取舍)
])
def test_temperature_cleaning(raw, expected):
    w = WeatherInfo(date="2026-10-01", day_temp=raw)
    assert w.day_temp == expected


def test_temperature_none_fails():
    # mode='before' 的校验器只处理 str;None 会落到 Union[int, str] 校验 → 应抛错
    with pytest.raises(ValidationError):
        WeatherInfo(date="2026-10-01", day_temp=None)
```

这里用到了**参数化**(`@pytest.mark.parametrize`):一份测试逻辑,喂 7 组输入,每组独立运行、独立报告——比复制 7 遍测试函数干净得多。先猜后跑:`None` 那条你猜对了吗?动手运行一次,让事实校准直觉,这是本课贯穿的方法。

## 20.4 单元测试:三种 JSON 提取策略

**前置确认:** 若第 13 课必做作业已完成,`app/agents/retry_parser.py` 里有现成的 `extract_json`;没做的话,把第 13 课的 `extract_json` 实现(带 `if e != -1` 完整围栏保护的那版)补进该文件——它和 `_parse_response` 342–354 行同思路,但独立成函数才可测。**这段经历本身就是测试课的一部分:不可测的代码,往往要先小幅重构(提函数、去副作用)才变得可测。**

新建 `tests/test_extract_json.py`,样本直接取自第 13 课实验 A:

```python
import json
import pytest
from app.agents.retry_parser import extract_json


@pytest.mark.parametrize("response,expected", [
    # 策略一: json 围栏 + 前后寒暄
    ('好的!```json\n{"a": 1}\n```希望有帮助', '{"a": 1}'),
    # 策略二: 裸围栏
    ('```json\n{"a": 1}\n```', '{"a": 1}'),
    # 策略三: 花括号截取(前后杂讯)
    ('计划如下 {"city": "北京"} 请查收', '{"city": "北京"}'),
    # 反直觉样本: 字符串值内含右花括号,rfind 能救回来
    ('{"a": "文本里有个}号"}', '{"a": "文本里有个}号"}'),
])
def test_extract_json_strategies(response, expected):
    assert json.loads(extract_json(response)) == json.loads(expected)


@pytest.mark.parametrize("bad", ["纯文本什么都没有", ""])
def test_extract_json_no_data_raises(bad):
    with pytest.raises(ValueError):
        extract_json(bad)
```

再看 `_parse_response` 与 `extract_json` 的一个行为差异,值得写一条对比测试:`_parse_response` 的策略一(`trip_planner_agent.py` 342–345 行)遇到"有 ```json 开头但没有闭合围栏"的截断输出时,`json_end` 会是 `-1`,切片结果为空串;而第 13 课的 `extract_json` 用 `e != -1` 挡住了它,会滑向策略三。**同一套策略,两份实现,行为分叉——这正是第 14 课之后你应该把 `_parse_response` 的提取段替换成 `extract_json` 调用的理由,写一条 TODO 注释并顺手完成它。**

## 20.5 单元测试:重试解析器(mock LLM 的标准姿势)

`parse_with_retry(query, call_llm)` 的精髓在第 13 课就点过:**`call_llm` 参数化,测试时传一个假函数**。这就是 mock 的最小形态——不用任何 mock 库,一个闭包就够了:

```python
import json
import pytest
from app.agents.retry_parser import parse_with_retry, MAX_RETRIES
from tests.fixtures import GOOD_PLAN_JSON   # 共享夹具,见 20.7


def test_retry_recovers_on_third_attempt():
    """前两次失败,第三次自修成功:应恰好调 3 次 LLM"""
    replies = iter(["这不是JSON", '{"city": "北京"}', GOOD_PLAN_JSON])
    calls = []

    def fake_llm(prompt: str) -> str:
        calls.append(prompt)
        return next(replies)

    plan = parse_with_retry("生成行程", fake_llm)
    assert plan.city == "北京"
    assert len(calls) == 3
    # 第 2 次起,提示词里应带上错误反馈(第 13 课 FIX_PROMPT 的作用)
    assert "未通过校验" in calls[1] or "错误" in calls[1]


def test_retry_exhausts_and_raises():
    """始终失败:轮数用尽后上抛,绝不做假数据(第 14 课的结论)"""
    def always_bad(prompt: str) -> str:
        return "还是不行"

    with pytest.raises(ValueError):
        parse_with_retry("q", always_bad)
```

注意第二条测试的断言对象是 `ValueError`(extract_json 对纯文本抛的)——它同时验证了第 14 课最重要的产品决定:**重试耗尽的行为是 raise,不是 fallback**。如果未来有人手滑把 `raise` 改回 `return self._create_fallback_plan(request)`,这条测试会立刻变红。测试是决定(决策)的存档。

## 20.6 打桩集成测试:plan_trip 的胶水逻辑

集成测试要回答的问题是:**四个 Agent 的输出有没有被正确地"接线"?** 把 `MultiAgentTripPlanner` 的四个 Agent 全换成桩,验证编排层(查询拼接 → 依次调用 → 解析)的接线质量。

先解决"构造难"的问题:`__init__` 会创建 LLM 和 MCPTool(拉起 uvx 子进程),测试里绝不能真跑。用 `object.__new__` 跳过 `__init__`,手动摆好属性:

```python
# tests/test_plan_trip.py
import json
import pytest
from app.agents.trip_planner_agent import MultiAgentTripPlanner
from app.models.schemas import TripRequest
from tests.fixtures import GOOD_PLAN_JSON, make_request


class StubAgent:
    """记录收到的查询、返回固定回复的假 Agent"""
    def __init__(self, reply):
        self.reply = reply
        self.last_query = None

    def run(self, query: str) -> str:
        self.last_query = query
        return self.reply


def make_planner():
    planner = object.__new__(MultiAgentTripPlanner)   # 跳过 __init__,不碰 LLM/MCP
    planner.attraction_agent = StubAgent("景点搜索结果: 故宫, 天安门...")
    planner.weather_agent = StubAgent("天气结果: 晴 25°C")
    planner.hotel_agent = StubAgent("酒店结果: 如家酒店...")
    planner.planner_agent = StubAgent(f"```json\n{GOOD_PLAN_JSON}\n```")
    return planner


def test_plan_trip_wires_all_outputs_into_planner():
    planner = make_planner()
    request = make_request()

    plan = planner.plan_trip(request)

    # 三路输出都应出现在发给规划 Agent 的查询里(接线完整性)
    assert "景点搜索结果" in planner.planner_agent.last_query
    assert "天气结果" in planner.planner_agent.last_query
    assert "酒店结果" in planner.planner_agent.last_query
    # 城市与天数被正确传递
    assert plan.city == "北京"
    assert len(plan.days) == request.travel_days


def test_plan_trip_with_llm_outage():
    """LLM 全挂(返回空串):原版会走 fallback 假数据;第 14 课改造后应 raise"""
    planner = make_planner()
    planner.attraction_agent = StubAgent("")
    planner.weather_agent = StubAgent("")
    planner.hotel_agent = StubAgent("")
    planner.planner_agent = StubAgent("")

    # 原版仓库代码: 断言返回了兜底计划(并思考这是不是你想要的)
    # 完成第 14 课改造后: 改为断言抛出异常
    plan = planner.plan_trip(make_request())
    assert plan.days  # fallback 计划也"成功"了——这句话本身值得你警惕
```

第二条测试就是 20.1 说的"会失败的桩":它把你第 14 课做的产品伦理决定重新摆上台面,并且**在仓库原版代码上它会通过**——因为 `_parse_response` 366–369 行和 `plan_trip` 275–279 行的 fallback 还在。完成第 14 课改造的读者,请把断言改成 `with pytest.raises(Exception): planner.plan_trip(request)`,让测试与你的架构决定一致。

再给第 11/12 课的异步版补一条(asyncio_mode = auto 下直接写 async def 即可):

```python
async def test_plan_trip_async_smoke():
    planner = make_planner()
    plan = await planner.plan_trip_async(make_request())
    assert plan.city == "北京"
```

(`plan_trip_async` 是你第 11 课新增的方法;桩的 `run` 是同步的,`asyncio.to_thread` 包着它照样能跑。)

### 完成标准

- [ ] `pytest -v` 全绿,测试总数 ≥ 15,且覆盖四块:JSON 提取、温度校验器、重试解析器、plan_trip 编排;
- [ ] 全程未发起任何真实 LLM / MCP / HTTP 调用(把网线拔了也能全绿);
- [ ] `test_plan_trip_with_llm_outage` 的断言与你的架构现状一致(原版 = fallback 存在;第 14 课后 = raise),并留有一行注释说明为什么;
- [ ] 把 `parse_with_retry` 的 `call_llm` 换成真 Agent 的那行主链路代码(第 13 课作业)在测试覆盖之下;
- [ ] `.pytest_cache/` 没有被提交——`backend/.gitignore` 早就为它留了位置,验证一下。

### 常见卡点

- **Q:`ModuleNotFoundError: No module named 'app'`?** 你站在了仓库根目录。`cd backend` 再跑 `pytest -v`;或者给 pytest.ini 加 `pythonpath = .`(pytest ≥ 7 支持)。
- **Q:测试之间互相污染?** `get_trip_planner_agent()` 是全局单例(`trip_planner_agent.py` 422–429 行),某个测试一旦真初始化了它,后续测试会复用脏实例。原则:**测试永远不碰单例 getter**,都走 `object.__new__` 自建实例;真碰了,写个 autouse fixture 在每条测试后 `_multi_agent_planner = None` 复位。
- **Q:异步测试报 `async def functions are not natively supported`?** `pytest-asyncio` 没装或 `pytest.ini` 里漏了 `asyncio_mode = auto`。
