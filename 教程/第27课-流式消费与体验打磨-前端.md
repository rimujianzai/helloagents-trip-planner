## 1.1 EventSource 及它的"POST 残疾"

浏览器对 SSE 的原生支持是 `EventSource`:

```ts
const es = new EventSource('/api/trip/plan/stream')
es.addEventListener('step', (e) => { /* e.data 是载荷 */ })
```

它自带三个好东西:自动解析 SSE 格式、按事件类型分发、断线自动重连(带 `Last-Event-ID`)。但它有一个对本项目致命的限制——**构造函数只发 GET 请求**,不能设置方法、不能带请求体、自定义 header 也受限。

而规划请求的参数(城市、日期、天数、偏好、自由输入)是一个不小的 JSON 对象(`schemas.py` 的 `TripRequest`):塞 query string 既笨重,又会把用户输入泄进各级访问日志;而且后端第 26 课实现的就是 POST 端点。**结论:放弃 `EventSource`,用 `fetch` 手写。** 作为补偿,fetch 给了我们两样 `EventSource` 没有的东西:任意 HTTP 方法与请求体,以及 `AbortController`——用户随时可以主动取消。

> 判断依据和第 12 课选 `def` / `async def` 是同一种思维方式:**先看标准件满足不了什么,再决定手写;手写的每一行都要有标准件给不了的理由。**

## 1.2 fetch + ReadableStream:手撕 SSE 解析器

在 `frontend/src/services/api.ts` 里新增(放在现有的 `generateTripPlan` 旁边,第 41–49 行):

```ts
export interface StreamEvent {
  event: string
  data: any
}

function parseSSEChunk(chunk: string): StreamEvent | null {
  let event = 'message'
  let data = ''
  for (const line of chunk.split('\n')) {
    if (line.startsWith('event:')) event = line.slice(6).trim()
    else if (line.startsWith('data:')) data += line.slice(5).trim()
  }
  if (!data) return null
  try { return { event, data: JSON.parse(data) } }
  catch { return { event, data } }          // 非 JSON 载荷(如 done)原样给
}

export async function streamTripPlan(
  formData: TripFormData,
  onEvent: (e: StreamEvent) => void,
  signal?: AbortSignal
): Promise<void> {
  const resp = await fetch(`${API_BASE_URL}/api/trip/plan/stream`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(formData),
    signal                                   // AbortController 的信号
  })
  if (!resp.ok || !resp.body) throw new Error(`流式请求失败: HTTP ${resp.status}`)

  const reader = resp.body.getReader()       // ReadableStream 逐块读取
  const decoder = new TextDecoder('utf-8')
  let buffer = ''

  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    buffer += decoder.decode(value, { stream: true })
    const parts = buffer.split('\n\n')
    buffer = parts.pop() ?? ''               // 最后一段可能不完整,留到下一轮
    for (const part of parts) {
      const ev = parseSSEChunk(part)
      if (ev) onEvent(ev)
    }
  }
  if (buffer.trim()) {                       // 流结束,冲刷残留
    const ev = parseSSEChunk(buffer)
    if (ev) onEvent(ev)
  }
}
```

这段不到 40 行的代码是本课含金量最高的知识点,两处必须彻底理解:

**① chunk ≠ 事件。** `reader.read()` 返回的是网络分包,大小和时机由 TCP 决定:一个 chunk 可能含半个事件、两个事件、或一个事件的前 80%。所以必须**攒进 buffer、按事件边界 `\n\n` 切分、把最后可能不完整的段留在 buffer 里等下一个 chunk**。`parts.pop()` 这一行就是这个"留尾"逻辑——删掉它,你会在真实网络下随机丢事件,而本地开发几乎复现不了(本地延迟低,常常一个 chunk 恰好一个事件)。这类"开发环境永远不复现"的 Bug,是流式处理的经典陷阱。

**② `{ stream: true }` 的 decoder。** 中文是多字节 UTF-8 字符(3 字节),一个 3 字节字符可能被 TCP 从中间劈开——前 2 字节在上一 chunk、第 3 字节在下一 chunk。`TextDecoder` 必须**跨调用保持状态**并用 `decode(value, { stream: true })` 告诉它"后面还有",它才会把半个字符先攒着。每次循环 `new TextDecoder()` 或者漏了 `stream: true`,中文就会随机乱码。

用 curl 验证过的协议(第 26 课 1.3 节)在这里被逐行"翻译"成对象——**协议知识 + 字节层细节,缺一个都会翻车。**

## 1.3 timeout: 120000 退役:超时语义的迁移

打开 `api.ts`,第 6–12 行:

```ts
const apiClient = axios.create({
  baseURL: API_BASE_URL,
  timeout: 120000, // 2分钟超时                // ← 第 8 行,本节主角
  headers: {
    'Content-Type': 'application/json'
  }
})
```

先理解它当年为什么存在:axios 的 `timeout` 计时的是**整个响应周期**。一次性接口"什么时候返回"完全不可知(30 秒–2 分钟,见第 26 课的时间账),不设上限的话,后端真挂了用户就永远转圈。`120000` 本质上是**对"我们不知道后端要多久"的粗暴补偿**——赌一次规划不会超过 2 分钟。赌输了(网络慢、模型慢)用户看到超时报错,其实后端可能还在正常干活。

流式方案下它被更精确的机制取代,三层职责各归其位:

1. **传输层:`streamTripPlan` 走 fetch,根本不经过 axios 实例**,`timeout` 对它没有管辖权;
2. **活性判断:由事件本身保证。** 连接里只要有事件持续到达,系统就是活的;真正需要担心的是"长时间没有任何事件"——这是**事件间隔**问题,不是总时长问题。设一个事件级看门狗(比如 60 秒无事件则 `AbortController.abort()` 并报"连接超时"),比一刀切的 2 分钟精确得多;
3. **用户主权:`AbortController` 让"取消"成为一等公民。** 旧方案里用户只能关页面;现在可以给个取消按钮,`abort()` 之后 fetch 立刻抛 `AbortError`。

**结论:`8 行`的 `timeout: 120000` 可以退役**——流式路径已不经过 axios,其余短接口(健康检查、图片)要超时也轮不到 2 分钟这个量级。删掉或改成更合理的短超时(如 10 秒),并在笔记里写清上面的职责迁移。**一个超时值的死亡,背后是错误处理模型的升级:从"赌总时长"到"看活性"。**

## 1.4 三态体验:用状态机组织加载 / 错误 / 成功

先看现状有多粗糙:`Home.vue:251` 的 `handleSubmit` 里,`261–277 行`是假进度(`setInterval` 每 500ms 加 10%,文案靠数值区间硬编码),`291 行`调一次性接口,`297–306 行`成功后写 `sessionStorage` 并跳转 `/result`。加载、数据、跳转搅在一个函数里,而"失败"只有一行 `message.error`(`312 行`)——没有重试,用户只能重新填表。

用状态机重新组织。流式规划的生命周期只有五态:

```
idle ──开始──▶ streaming ──收到plan──▶ success
                 │  ▲
                 └──┴─收到error/看门狗触发──▶ error(可 retry 回 streaming)
```

落到代码,是一份时间线状态(composable 中的核心结构):

```ts
interface StepState {
  key: string                                   // attractions / weather / hotel / planner
  label: string
  status: 'pending' | 'running' | 'done' | 'error'
  startedAt?: number
  finishedAt?: number
}

const steps = ref<StepState[]>([
  { key: 'attractions', label: '搜索景点', status: 'pending' },
  { key: 'weather',     label: '查询天气', status: 'pending' },
  { key: 'hotel',       label: '推荐酒店', status: 'pending' },
  { key: 'planner',     label: '生成计划', status: 'pending' }
])
```

`onEvent` 的映射规则(与第 26 课的事件清单一一对应):

- 收到 `stage` 的第一条事件 → 该步 `running`,记 `startedAt`;
- 收到该步的完成事件 → `done`,记 `finishedAt`( UI 就能显示真实耗时,**这是假进度条永远给不了的数字**);
- 收到 `error` → 当前 running 的步骤标 `error`,整体进入 error 态,把 `data.message`(后端的诚实报错,第 14 课)显示出来;
- 收到 `plan` → 存 `sessionStorage` 的 `tripPlan`,进入 success 态。

> 并行化后,景点/天气/酒店三步会**同时 running**——时间线 UI 要支持多步同亮,别按串行假设写"点亮下一步"。这本身又是第 11 课并行化的直观展示。

**与第 24 课结构的衔接:** 这份状态和 `onEvent` 映射逻辑不该住在任何 `.vue` 文件里——它是典型的"有状态逻辑",放进第 24 课抽出的 `useTripPlan`(或新建 `useStreamingPlan`)composable,UI 组件只消费状态。时间线本身做成小组件(如 `PlanTimeline.vue`),错误卡片做成 `PlanError.vue`。第 24 课练的"职责拆分",这一课立刻得到回报:**流式是横切增强,组件化让它可以只加不改。**

### 集成路径:流式发生在哪个页面?

推荐**方案 A(本课实验采用):把等待搬到结果页。** 流程:

1. `Home.vue` 的 `handleSubmit` 删掉 261–277 行的假进度,只做:`sessionStorage.setItem('tripFormRequest', JSON.stringify(formData))` → `router.push('/result')`——用户点击后**立刻**进入结果页;
2. `Result.vue` 挂载时(现有 `onMounted`,`329–339 行`)先查 `tripFormRequest`:有则启动 `streamTripPlan`,时间线 UI 显示在地图卡片上方;收到 `plan` 事件后写入原有的 `tripPlan` 渲染链路(`330 行`的读取逻辑原样复用),并清掉 `tripFormRequest`;
3. 兼容旧路径:没有 `tripFormRequest` 但有 `tripPlan`(旧会话)→ 直接渲染,行为与现在完全一致。

方案 A 的好处:用户更早进入"目的地页面",时间线、地图骨架、第 25 课的图层控件同屏过渡,体验是"页面在生长"而不是"弹窗在转圈"。方案 B(留在 `Home.vue`、时间线替换现在的加载弹窗)改动最小,若你不想动 `Result.vue` 可选它——但要做,就做到底,别留一个"半流式"。

### 步骤

1. **api.ts**(1.2 节代码):新增 `StreamEvent`、`parseSSEChunk`、`streamTripPlan`(带 `signal` 参数);同时按 1.3 节处理第 8 行的 `timeout`;
2. **composable**:新建或扩展 `useStreamingPlan`,内含 `steps` 状态机、`startStreaming(formData)`、`cancel()`(调 `abort()`)、`retry()`(用保存的 formData 重新 `startStreaming`);
3. **Home.vue**:改 `handleSubmit`(删 261–277 假进度,存 `tripFormRequest`,跳转);
4. **Result.vue**:onMounted 检测 `tripFormRequest` → 渲染时间线组件 → `startStreaming`;`plan` 事件到达后写 `tripPlan`、清 `tripFormRequest`、`nextTick` 后走原有地图初始化(第 25 课的图层切换与联动应当自动工作);
5. **错误态 UI**:error 卡片显示后端 message + 「重试」按钮(绑 `retry()`)+「返回首页」;用 DevTools 的 Network 面板设 Offline 模拟断网验证;
6. **看门狗**:60 秒无任何事件则 abort,提示"连接超时,请重试"(用一个记录 lastEventTime 的定时检查实现,注意组件卸载时清定时器——第 23 课讲过的生命周期清理);
7. **端到端验证**:真实生成一次;中途点取消;断网恢复后重试;确认 `POST /api/trip/plan`(旧接口)依然可用。

### 完成标准

- [ ] 点击"生成"后立即进入结果页,时间线四步随真实事件点亮(并行化后前三步同时 running),每步显示真实耗时;
- [ ] 假进度条与 `setInterval` 已从 `Home.vue` 中删除;
- [ ] 停掉后端或断网:时间线进入错误态,显示后端 `error` 事件里的 message,点「重试」能完整重走流程;

- [ ] `api.ts:8` 的 2 分钟超时已按 1.3 节处理,你能向别人解释"总时长超时"和"事件间隔超时"的区别;
- [ ] 旧接口 `POST /api/trip/plan` 与旧渲染路径(sessionStorage 直接有 tripPlan)不受影响。

### 常见卡点

- **"事件偶尔收到、偶尔丢,尤其最后一个 plan 事件?"** 九成是 chunk 边界:检查 `parts.pop()` 的留尾逻辑和流结束后的 buffer 冲刷(1.2 节代码末尾的 `if (buffer.trim())`)。后端也可能有问题——`plan` 事件后必须输出空行,否则它和 `done` 粘成一个块。
- **"中文随机乱码?"** `decoder.decode(value, { stream: true })` 的 `stream: true` 漏了,或在循环里反复 `new TextDecoder()`。回看 1.2 节要点②。
- **"本地好好的,build 出来的版本连不上后端?"** `fetch` 直连 `API_BASE_URL`(`api.ts:4`),走的是绝对地址;开发时的 `vite.config.ts:15-20` 代理只在 dev server 生效。生产环境要么后端支持 CORS,要么(推荐)让 nginx 把 `/api` 反代到后端——第 30 课一起解决。
