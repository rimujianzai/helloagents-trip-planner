## 19.1 先测量:print 到底有多少、都是什么

第 18 课的下节预告说"40+ 处 print"——**别信任何文档的数字,包括本课程自己的。动手量一遍**:

```bash
cd backend
grep -rn "print(" app --include="*.py" | wc -l          # 总数
grep -rc "print(" app --include="*.py" | grep -v ":0" | sort -t: -k2 -rn   # 按文件分布
```

2026-09-11 的实测结果是 **90 处**,分布如下:

| 文件 | 数量 | 主要内容 |
|---|---|---|
| `app/agents/trip_planner_agent.py` | 32 | 启动横幅、四步骤进度、解析失败警告 |
| `app/services/amap_service.py` | 15 | MCP 原始响应截断(`result[:200]`)、错误 |
| `app/api/main.py` | 13 | 启动/关闭横幅、配置打印 |
| `app/api/routes/trip.py` | 10 | 请求横幅、步骤进度、错误 |
| `app/config.py` | 10 | `print_config` 调试输出、配置警告 |
| `app/api/routes/map.py` / `poi.py` / `services/llm_service.py` | 各 3 | 错误、初始化信息 |
| `app/services/unsplash_service.py` | 1 | 错误 |

再按"内容类型"分一遍(用 emoji 当线索,因为现在的级别全靠表情符号表达):

```bash
grep -rn "print(.*❌" app --include="*.py" | wc -l   # 错误: 16 处
grep -rn "print(.*✅" app --include="*.py" | wc -l   # 成功: 6 处
grep -rEn "print\(.*(🔄|🚀|📍|🌤|🏨|📋|📥)" app --include="*.py" | wc -l   # 步骤进度: 10 处
grep -rn "print(.*⚠" app --include="*.py" | wc -l   # 警告: 2 处
grep -rn "print(.*\[:200\]" app --include="*.py" | wc -l   # 原始响应调试: 8 处
```

### print 调试的四个结构性局限

拿着这份分类表,逐条对号入座:

1. **无级别。** "错误"和"进度"只有表情符号的区别,机器无法按级别过滤——想把错误单独捞出来,只能人肉看 90 处输出。
2. **无时间。** 一条 `📍 步骤1: 搜索景点...` 出现在什么时候、花了多久,没有任何记录。第 17 课你计时外部调用靠的是临时加代码,而这些代码加完就成了新的 print 债。
3. **无法关闭。** 上线后这些输出照样全量打:既拖慢请求(终端 I/O 是同步阻塞的),又把真正要紧的日志淹掉。你没有"只留 ERROR"的开关。
4. **难落盘、难检索。** 输出只活在当前终端里,进程一重启就没;无法回溯"昨晚那次失败",更没有检索能力。

对本项目还有**第五个局限,也是最疼的一个:无法关联**。两个请求并发时,它们的日志会交错打印,你分不清哪行属于谁——第 12 课压测时你应该已经见过这个混乱现场。这是 19.5 节 request_id 要解决的问题。

## 19.2 loguru 五分钟入门

好消息:`backend/requirements.txt` 第 21 行早就装好了它——`loguru>=0.7.0`,只是从没人用过。loguru 的核心卖点:开箱即用的级别、时间戳、颜色,以及一条语句完成的落盘轮转。

```python
from loguru import logger

logger.debug("调试细节,默认不显示")       # DEBUG
logger.info("正常进度")                  # INFO
logger.success("成功,比 info 更醒目")     # SUCCESS(loguru 特有级别)
logger.warning("值得注意但未失败")         # WARNING
logger.error("失败,需要关注")            # ERROR
logger.exception("失败,自动附带堆栈")     # 在 except 块里用,等价 error + traceback
```

默认 logger 只往标准错误流打一条带时间戳的彩色行。真正的威力在 `logger.add(目标, ...)`——可以叠加多个"接收端"(sink):控制台一个、文件一个、级别各不相同:

```python
logger.remove()                       # 移除默认 sink,重新配置
logger.add(sys.stderr, level="INFO")  # 控制台只看 INFO 以上
logger.add("logs/app_{time:YYYY-MM-DD}.log", level="DEBUG")  # 文件里存 DEBUG 以上
```

这就是 19.4 节落盘配置的全部地基。

## 19.3 全局替换:先分类,再动手

替换不是 90 次"查找-替换",而是**先按 19.1 的分类映射到级别,再逐类动手**:

| 现状 | 目标级别 | 理由 |
|---|---|---|
| `❌ ...失败` | `logger.exception`(在 except 内)/ `logger.error` | 需要堆栈时必须用 exception |
| `⚠️ ...警告` | `logger.warning` | |
| `✅ ...成功` | `logger.success` / `logger.info` | 一次性初始化成功用 info 即可 |
| 步骤进度(📍🚀 等) | `logger.info` | 请求主线剧情 |
| 启动横幅(`=`*60 那种) | `logger.info`(合并成一条多行消息) | 横幅是给人看的,一条消息足够 |
| `result[:200]` 原始响应 | `logger.debug` | 平时噪音,排查时把文件 sink 开到 DEBUG 就有 |

三个代表性改法(其余照此办理):

**① `trip.py` 的请求横幅(31–36 行)——六条 print 合并成一条结构化日志:**

```python
# 改造前:6 条 print 拼横幅(31–36 行)
# 改造后:
logger.info(f"收到旅行规划请求: city={request.city}, dates={request.start_date}~{request.end_date}, days={request.travel_days}")
```

**② `_parse_response` 的失败路径(`trip_planner_agent.py` 366–369 行)——这是全项目最需要堆栈的地方:**

```python
except Exception as e:
    logger.exception(f"解析响应失败: {type(e).__name__}: {e}")   # 堆栈自动进日志
    return self._create_fallback_plan(request)
```

(若你已完成第 14 课的"诚实报错"改造,这里是 `raise`——那就更简单,让上层的异常处理统一 `logger.exception`。)

**③ `amap_service.py` 的原始响应(84、113、179、210、238 行)——降级为 DEBUG,保留原文:**

```python
logger.debug(f"POI搜索原始响应: {result[:500]}")
```

顺带把截断从 200 放宽到 500——文件 sink 不怕长,而原始响应是第 15 课排错时的救命稻草。

**一个边界要说清楚:hello-agents 框架内部的 print 改不了。** 框架源码不在本仓库,它的输出你也无权修改——能做的是:(a) 靠本仓库自己 90 处的日志足够定位业务问题;(b) 框架若往 stdout 打日志,可以写一个重定向 sink 把 stdout 捕获进 loguru(进阶技巧,选做作业)。**遇到"框架里到底发生了什么"的问题,正确的路径是去框架源码里定位(第 7 课练过),而不是指望日志替你回答一切。**

## 19.4 落盘、轮转与保留

新建 `backend/app/logging_setup.py`,这是全项目日志的唯一配置点:

```python
"""loguru 全局日志配置"""
import sys
from loguru import logger
from ..config import get_settings

_FORMAT = (
    "<green>{time:YYYY-MM-DD HH:mm:ss.SSS}</green> | "
    "<level>{level: <8}</level> | "
    "<cyan>{extra[request_id]}</cyan> | "
    "<cyan>{name}</cyan>:<cyan>{line}</cyan> - <level>{message}</level>"
)

def setup_logging():
    settings = get_settings()
    logger.remove()
    # 控制台:按 .env 的 LOG_LEVEL(config.py 47 行)过滤
    logger.add(sys.stderr, level=settings.log_level, format=_FORMAT)
    # 文件:全量 DEBUG,按天轮转,留 14 天,自动压缩
    logger.add(
        "logs/backend_{time:YYYY-MM-DD}.log",
        level="DEBUG",
        format=_FORMAT,
        rotation="00:00",          # 每天 0 点切新文件
        retention="14 days",       # 超过 14 天自动删除
        compression="zip",         # 旧日志压缩省空间
        encoding="utf-8",          # Windows 下必加,否则 emoji/中文可能炸
        enqueue=True,              # 后台线程写盘,不阻塞请求
        diagnose=False,            # 生产建议关:堆栈里不展开变量值(防泄密)
    )
    return logger.patch(lambda r: r["extra"].update(request_id=request_id_ctx.get()))

# request_id 的容器,19.5 节用到;先给默认值 "-",启动期日志用它
import contextvars
request_id_ctx: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")

logger = setup_logging()
```

三个工程细节:

- **`encoding="utf-8"` 在 Windows 上是刚需**——你的日志里全是中文和 emoji,默认编码可能直接抛 `UnicodeEncodeError`;
- **`rotation`/`retention`/`compression` 三件套**就是"轮转"的全部含义:每天一个文件、自动清理、自动压缩,不写一行管理代码;
- **`logs/` 目录不用进 `.gitignore`**——根 `.gitignore` 第 41 行的 `*.log` 和 `backend/.gitignore` 的日志段已经把 `*.log` 全盖住了。但注意它们只匹配 `.log` 结尾的文件,本课不改动这一点,正好。

最后在 `main.py` 的启动逻辑里(`@app.on_event("startup")` 处理器开头)调用 `setup_logging()`,其余模块统一 `from ..logging_setup import logger`(或在 `logging_setup.py` 里也 `from loguru import logger` 保持同名导入)。

## 19.5 request_id:一次请求的身份证

目标:同一请求的所有日志行携带同一个短 ID,并发请求互不污染,`grep` 一个 ID 就能回放全程。

**为什么不能用一个全局变量?** 因为全局变量在并发下会被互相覆盖:请求 A 刚设好,请求 B 一进来就把它改了。正确工具是 **`contextvars`**——每个执行上下文( roughly, 每个请求协程)有自己独立的一份值,互不可见。配合 `logger.patch`,每条日志落盘前从当前上下文里取 ID(见 19.4 代码里的 `extra[request_id]`)。

**注入点选在中间件**——它是每个 HTTP 请求的必经之路。在 `main.py` 里加:

```python
import uuid
from ..logging_setup import logger, request_id_ctx

@app.middleware("http")
async def request_context_middleware(request, call_next):
    rid = uuid.uuid4().hex[:8]                 # 8 位短 ID,足够回放且好复制
    token = request_id_ctx.set(rid)
    try:
        response = await call_next(request)
    finally:
        request_id_ctx.reset(token)            # 请求结束必须复位,防止上下文泄漏
    response.headers["X-Request-ID"] = rid     # 返回给前端,排障时用户能报这个号
    return response
```

**线程边界的两个真相**(对应第 11/12 课的改造):

1. `asyncio.to_thread(...)` 会**拷贝**当前上下文再进线程——所以你并行化的三路 Agent 日志**自动**带上 request_id,不用改一行;
2. 裸 `threading.Thread` **不会**拷贝——如果某处代码自己开线程打日志,ID 会变回 `-`。兜底方案是**显式透传**:给 `plan_trip(request, request_id: str = "-")` 加参数,在线程函数里手动 `request_id_ctx.set(request_id)`。这也是任务书里"中间件注入 + 各层透传"的完整含义:**常规路径靠 contextvars 隐式贯穿,跨不过去的边界靠参数显式带**。

还有一处盲区要诚实说明:uvicorn 自己的访问日志(请求耗时那行)走的是标准 `logging` 模块,不经过 loguru,所以**没有** request_id。想统一,需要写一个 `InterceptHandler` 把标准 logging 重定向进 loguru——这是选做作业。

### 完成标准

### 常见卡点

- **Q:控制台 emoji 乱码或报 `UnicodeEncodeError`?** Windows 终端编码问题。文件 sink 已有 `encoding="utf-8"`;控制台可设环境变量 `PYTHONUTF8=1` 再启动,或把控制台 sink 的消息里的 emoji 顺手删掉(级别色块已经承担了它的职责)。
- **Q:所有日志的 request_id 都是 `-`?** 三个排查点:中间件是否注册在路由生效之前;是否用的 `request_id_ctx.set` 而不是赋值;是否在 `startup` 里打的日志(那是请求上下文之外,`-` 是正常的)。
- **Q:`logger = logger.patch(...)` 之后别的模块拿到的还是旧的?** 各模块应统一 `from app.logging_setup import logger`(拿打完补丁的实例),而不是直接 `from loguru import logger`。全项目保持一种导入方式。
