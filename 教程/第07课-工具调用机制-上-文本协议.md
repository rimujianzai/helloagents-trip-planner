## 7.1 从 291 行说起:一个被"剧透"的 Agent

打开 `backend/app/agents/trip_planner_agent.py`,第 1 课你已经见过这个方法,现在换一个视角再看它:

```python
def _build_attraction_query(self, request: TripRequest) -> str:
    """构建景点搜索查询 - 直接包含工具调用"""
    keywords = []
    if request.preferences:
        # 只取第一个偏好作为关键词
        keywords = request.preferences[0]
    else:
        keywords = "景点"

    # 直接返回工具调用格式
    query = f"请使用amap_maps_text_search工具搜索{request.city}的{keywords}相关景点。\n[TOOL_CALL:amap_maps_text_search:keywords={keywords},city={request.city}]"
    return query
```

(`trip_planner_agent.py` 281–292 行,注入的 `[TOOL_CALL:...]` 在第 291 行)

注意第 291 行:发给景点 Agent 的用户消息里,**工具调用本身已经被代码写好了**。LLM 拿到这段话,几乎只剩一个动作——把方括号里的内容复述一遍。也就是说,这条链路里"调用哪个工具、传什么参数"是 `_build_attraction_query` 决定的,不是 LLM 决定的。这就是学习建议.md 说的"伪自主"。

本课的重点不是批判这个设计,而是借它看清整条机制:**不管 LLM 是被剧透还是自己想出来,只要输出里出现了 `[TOOL_CALL:...]` 这串文本,后面发生的每一件事都一模一样**。先把机制吃透,第 8 课才有资格评判"剧透"该不该删。

顺带一个阅读警觉点:`keywords` 在 283 行初始化为列表,286 行却被赋成字符串——类型不一致但恰好能跑,这类"碰巧没错"的代码是第 21 课 Bug 狩猎的编外成员。

## 7.2 文本协议长什么样:同一件事,写了三遍

`[TOOL_CALL:工具名:参数1=值1,参数2=值2]` 是 hello-agents 框架与 LLM 之间的一份"格式合同"。有意思的是,为了让 LLM 守约,项目里这份合同被写了**三遍**:

**第一遍:项目自己的系统提示词。** 三个工具型 Agent 的提示词都包含格式说明和 few-shot 示例(第 6 课你改过它们):

```python
ATTRACTION_AGENT_PROMPT = """你是景点搜索专家。你的任务是根据城市和用户偏好搜索合适的景点。

**重要提示:**
你必须使用工具来搜索景点!不要自己编造景点信息!

**工具调用格式:**
使用maps_text_search工具时,必须严格按照以下格式:
`[TOOL_CALL:amap_maps_text_search:keywords=景点关键词,city=城市名]`
...(few-shot 示例在 23–27 行,略)
```

(`trip_planner_agent.py` 13–33 行;天气版格式约定在 42 行,酒店版在 63 行)

**第二遍:框架自动注入的系统提示词。** 这是大多数人的盲区——你在第 7.3 节会看到,`SimpleAgent` 检测到你给它注册过工具后,会**自动**往系统提示词后面追加一整段"可用工具 + 调用格式"说明。你没写它,它在那里。

**第三遍:用户消息里的预注入。** 就是 291 行那串,只在景点 Agent 生效。

三遍合同指向同一个工具名:`amap_maps_text_search`。这个名字是**拼**出来的——`name="amap"`(`trip_planner_agent.py` 169 行)加上 MCP 服务器里的原始工具名 `maps_text_search`,框架用 `amap_` 前缀把两者粘起来。"展开 + 加前缀"的机制第 10 课彻底拆开,今天先记住结论:**LLM 看到的工具名带前缀,真正发给 MCP 服务器的名字不带**。

## 7.3 闭环第一步:LLM 输出从哪来

定位方法(现在就可以试):

```bash

```

`SimpleAgent.run`(0.2.9 的 `simple_agent.py`,方法从 246 行开始)构造消息列表时,第一件事就是处理系统提示词:

```python
def _get_enhanced_system_prompt(self) -> str:
    """构建增强的系统提示词，包含工具信息"""
    base_prompt = self.system_prompt or "你是一个有用的AI助手。"
    if not self.enable_tool_calling or not self.tool_registry:
        return base_prompt

    tools_description = self.tool_registry.get_tools_description()
    ...
    tools_section = "\n\n## 可用工具\n"
    tools_section += tools_description + "\n"
    tools_section += "\n## 工具调用格式\n"
    tools_section += "`[TOOL_CALL:{tool_name}:{parameters}]`\n\n"
    ...
```

(0.2.9 `simple_agent.py` 41–76 行,节选)

而工具清单本身来自注册表,每行就是"`名字: 描述`"一句话(`get_tools_description`,0.2.9 `registry.py` 116–133 行)。这就是 7.2 说的"第二遍合同"。请立刻意识到它的两个后果:

1. **参数 schema 在文本协议下是看不见的。** 工具清单只有名字和一句话描述,LLM 根本不知道 `maps_text_search` 有哪些参数、哪些必填——只能靠你提示词里的示例猜。这是文本协议可靠性的第一块短板,第 8 课对比原生 Function Calling 时会再拿出来称重;
2. **每一轮请求都携带全部工具清单。** amap-mcp-server 展开后有几十个工具(数量看后端启动日志打印的"工具数量",`amap_service.py` 37 行),这些 token 每一轮 LLM 调用都要重复付一遍。

消息列表组装完成后,发起第一次 LLM 调用:

```python
response = self.llm.invoke(messages, **kwargs)
```

(0.2.9 `simple_agent.py` 285 行;`HelloAgentsLLM.invoke` 在 `core/llm.py` 320–335 行,就是第 5 课讲过的 `chat.completions.create` 非流式调用,返回 `choices[0].message.content`)

## 7.4 闭环第二、三步:正则解析与参数"猜谜"

LLM 返回的只是一段普通文本,框架用一条正则把工具调用捞出来:

```python
def _parse_tool_calls(self, text: str) -> list:
    """解析文本中的工具调用"""
    pattern = r'\[TOOL_CALL:([^:]+):([^\]]+)\]'
    matches = re.findall(pattern, text)

    tool_calls = []
    for tool_name, parameters in matches:
        tool_calls.append({
            'tool_name': tool_name.strip(),
            'parameters': parameters.strip(),
            'original': f'[TOOL_CALL:{tool_name}:{parameters}]'
        })

    return tool_calls
```

(0.2.9 `simple_agent.py` 78–91 行)

花 30 秒读懂这条正则的两个约束:`[^:]+` 意味着**工具名里不能有冒号**,`[^\]]+` 意味着**参数串里不能有 `]`**。对"城市=北京"这类参数绰绰有余,但对复杂参数(嵌套结构、带右括号的文本)就会截断——记住这两条,7.7 节的失败模式你就能自己推出来。

解析出的是**字符串**,而工具执行需要**字典**。中间隔着一层我称之为"参数猜谜"的转换:

```python
def _parse_tool_parameters(self, tool_name: str, parameters: str) -> dict:
    """智能解析工具参数"""
    param_dict = {}

    # 尝试解析JSON格式
    if parameters.strip().startswith('{'):
        try:
            param_dict = json.loads(parameters)
            ...  # JSON 解析成功,做类型转换后直接返回
        except json.JSONDecodeError:
            pass

    if '=' in parameters:
        if ',' in parameters:                      # 多参数: action=search,query=Python
            pairs = parameters.split(',')          # 注意:只认英文逗号!
            for pair in pairs:
                if '=' in pair:
                    key, value = pair.split('=', 1)
                    param_dict[key.strip()] = value.strip()
        # ...(单参数 key=value 同理,见源码)

        # 类型转换
        param_dict = self._convert_parameter_types(tool_name, param_dict)
        ...
```

(0.2.9 `simple_agent.py` 114–154 行,节选)

三级策略:像 JSON 就按 JSON 解;像 `key=value` 就按逗号切;都不像就把整串塞给 `{"input": ...}`。最后还有一步值得表扬的补救——`_convert_parameter_types`(156–211 行)会去查工具的参数定义,把 `"120"` 转成数字 `"120" → 120`。而它查到的参数定义,恰恰来自 MCP 工具的 `input_schema`(JSON Schema)——**schema 一直都在,只是文本协议没把它给 LLM 看,只在背后偷偷用来纠错。**

注意 `split(',')` 只认英文逗号:LLM 输出中文逗号 `keywords=历史文化,city=北京` 的那一刻,`city` 参数就整个丢失了。"全角字符"事故是中文场景下文本协议最常见的翻车点。

## 7.5 闭环第四步:从一行文本到高德 API

执行环节是一条四层的调用链,每层都真实存在于你读过的代码里:

```python
def _execute_tool_call(self, tool_name: str, parameters: str) -> str:
    """执行工具调用"""
    ...
    try:
        # 获取Tool对象
        tool = self.tool_registry.get_tool(tool_name)
        if not tool:
            return f"❌ 错误：未找到工具 '{tool_name}'"

        # 智能参数解析
        param_dict = self._parse_tool_parameters(tool_name, parameters)

        # 调用工具
        result = tool.run(param_dict)
        return f"🔧 工具 {tool_name} 执行结果：\n{result}"

    except Exception as e:
        return f"❌ 工具调用失败：{str(e)}"
```

(0.2.9 `simple_agent.py` 93–112 行)

四层链路从上到下:

| 层 | 代码位置 | 做什么 |
|---|---|---|
| 1. SimpleAgent | 0.2.9 `simple_agent.py` 93–112 行 | 按名字从注册表取出工具,传入参数字典 |
| 2. MCPWrappedTool | 0.2.9 `mcp_wrapper_tool.py` 100–118 行 | 把参数包成 `{"action": "call_tool", "tool_name": "maps_text_search", "arguments": {...}}`,转交父 MCPTool——注意工具名在这里**去掉了 `amap_` 前缀** |
| 3. MCPTool | 0.2.9 `protocol_tools.py` 339–466 行 | 新建一条到 MCP 服务器的连接,执行 `call_tool`,把结果包成文本返回 |
| 4. MCP 服务器 | `uvx amap-mcp-server` 子进程 | 调高德 API,返回 JSON |

对比一下你在 `amap_service.py` 里见过的"不经 Agent 的直接调用"(57–91 行的 `search_poi`):

```python
result = self.mcp_tool.run({
    "action": "call_tool",
    "tool_name": "maps_text_search",
    "arguments": {"keywords": keywords, "city": city,
                  "citylimit": str(citylimit).lower()}
})
```

(`amap_service.py` 71–79 行;同样的写法还出现在天气 105–111 行、路线 173–177 行、地理编码 204–208 行、POI 详情 230–236 行)

看到了吗?**服务层手动构造的字典,和第 2 层 MCPWrappedTool 自动构造的字典,结构完全相同。** Agent 的"魔法"到此揭晓:所谓智能体调用工具,最终就是有人(注入的代码或 LLM 自己)写出一行 `[TOOL_CALL:...]` 文本,框架解析成这个字典,然后执行。两种通道殊途同归——这也是第 1 课"双通道"设计(1.4 节)的真正含义。

MCP 这一层的内部(子进程如何启动、消息长什么样)是第 10 课的主角,本课先按下不表。

## 7.6 闭环第五、六步:结果回填与再请求

工具结果怎么"喂"回 LLM?看 `run` 循环的核心段落:

```python
while current_iteration < max_tool_iterations:
    response = self.llm.invoke(messages, **kwargs)
    tool_calls = self._parse_tool_calls(response)

    if tool_calls:
        tool_results = []
        clean_response = response
        for call in tool_calls:
            result = self._execute_tool_call(call['tool_name'], call['parameters'])
            tool_results.append(result)
            clean_response = clean_response.replace(call['original'], "")

        # 构建包含工具结果的消息
        messages.append({"role": "assistant", "content": clean_response})
        tool_results_text = "\n\n".join(tool_results)
        messages.append({"role": "user", "content": f"工具执行结果：\n{tool_results_text}\n\n请基于这些结果给出完整的回答。"})
        current_iteration += 1
        continue

    # 没有工具调用，这是最终回答
    final_response = response
    break
```

(0.2.9 `simple_agent.py` 283–313 行,`max_tool_iterations` 默认值为 3,见 246 行方法签名)

这一段有五个必须刻进脑子的细节:

1. **回填用的角色是 `user`,不是专门的 tool 角色。** 框架把工具结果包装成一句"工具执行结果:……请基于这些结果给出完整的回答",以用户身份塞进对话。原生 Function Calling 有专门的 `role="tool"` 消息——对比是第 8 课的核心内容。
2. **LLM 原始输出里的 `[TOOL_CALL:...]` 被抹掉后**才存入 assistant 消息(`clean_response`),避免下一轮 LLM 看到自己上次的调用串而被带偏。
3. **一次输出多个 `[TOOL_CALL:...]` 会被全部执行**(295–299 行的 for 循环)。
4. **终止条件是"输出里没有工具调用"**,而不是"任务完成"。LLM 说收工,循环才收工——LLM 说了不算的时候,见下一条。
5. **每轮循环都把整个 `messages` 重发一遍**,包括系统提示词、完整工具清单、历史消息、工具结果。一次 `run()` 内部 2–3 轮 LLM 往返,token 消耗是滚雪球的。

还有个框架级的隐患,请你现在就试着推演:如果 3 轮用完,`final_response` 还是空,316–317 行会再补一次 `invoke`——但这次调用**不再检查输出里是否含 `[TOOL_CALL]`**。假如这次输出仍然是一个工具调用串,它会被原样当作 `run()` 的返回值,一路传回 `plan_trip`(245 行),被当作"景点搜索结果"拼进规划提示词(306–307 行)。错误的形态就这样流到了下游。你不需要修它,但你需要**知道它存在**——第 8 课的实验里你可以亲眼验证一次。

把闭环拼起来(编号对应上面五个细节与本节各步):

```
SimpleAgent.run()
  │ 组装 messages(系统提示词+工具清单+历史+用户消息)
  ▼
① llm.invoke ──输出──▶ "…[TOOL_CALL:amap_maps_text_search:keywords=…,city=…]"
  ▲                                │
  │                                ▼
  │                    ② 正则解析 → ③ 参数猜谜 → ④ MCPWrappedTool.run
  │                                                    │ → MCPTool.run → MCP 服务器
  │                                                    ▼
  └── ⑥ 无 TOOL_CALL 则 break ◀── ⑤ 结果包装成 user 消息回填 messages
```

## 7.7 失败模式清单:文本协议在赌什么

把 7.4–7.6 的短板汇总成一张表。第 8 课做三组对照实验时,这张表就是你的"预言清单"——先预测,再验证:

| # | 失败模式 | 根源 | 典型表现 |
|---|---|---|---|
| 1 | LLM 直接回答,不调工具 | 格式合同靠提示词约束,没有硬性强制 | 返回一段编造的景点介绍,循环第 1 轮就 break |
| 2 | 格式漂移 | 正则只认英文标点、半角方括号 | 中文逗号导致 `city` 参数丢失;全角括号导致解析失败 |
| 3 | 参数名拼错 | LLM 看不到参数 schema,只能凭示例猜 | MCP 返回"缺少参数 citylimit"类错误 |
| 4 | 超限后泄漏 | 补发的那次 invoke 不再检查 TOOL_CALL | 下游收到一串 `[TOOL_CALL:...]` 原文当"结果" |
| 5 | 错误自纠失效 | 工具报错文本回填后,LLM 可能继续错下去 | 连续 3 轮输出同样错误的调用 |

客观说,文本协议并非一无是处:**它对模型零要求**——任何能输出文本的模型都能接,实现也只有一条正则的复杂度。理解它的适用边界,比断言"它落后"更有工程价值。

在 `run` 方法内的 `response = self.llm.invoke(messages, **kwargs)`(0.2.9:285 行)前后插入日志(整体可删除):

```python
import os as _os
_TRACE = _os.getenv("TOOL_TRACE") == "1"
if _TRACE:
    print(f"\n===== 第 {current_iteration + 1} 轮 | LLM 输入 {len(messages)} 条消息 =====")
    for _m in messages:
        print(f"[{_m['role']}] {_m['content'][:150].replace(chr(10), ' ')}...")

response = self.llm.invoke(messages, **kwargs)   # ← 原有语句保持不变

```

注意日志开关用环境变量 `TOOL_TRACE` 守卫:不开开关时框架行为与原来完全一致,后端服务不受影响——这是改第三方源码时保住自己的标准做法。

```python

运行:cd backend 后执行
  Git Bash:    TOOL_TRACE=1 python tool_trace.py
  PowerShell:  $env:TOOL_TRACE="1"; python tool_trace.py

    auto_expand=True,
)
```

### 常见卡点

- **"pip show 找不到 hello-agents,但我明明跑通过项目"** —— 你大概率有多个 Python 环境。用启动后端的那同一个环境执行(如 `backend\.venv\Scripts\pip show hello-agents`);还找不到就按步骤 1 的版本约束装一次。
- **"我改了 site-packages,后端的行为会不会坏?"** —— 不会,日志有 `TOOL_TRACE` 开关守卫;实验完想彻底还原就执行 `cp simple_agent.py.bak simple_agent.py`。这也是为什么步骤 2 强制先备份。
- **"第 1 轮输出不是 TOOL_CALL,而是直接回答"** —— 先确认 `add_tool` 真的成功(脚本会打印工具数;为 0 就检查 `expandable = True`——没有它注册表不展开,这正是 `trip_planner_agent.py` 175 行存在的原因)。注册正常仍不调用,温度设 0(`agent.run(..., temperature=0)`)再试,并如实记为一次"失败模式 1"的现场样本。
