## 2.1 先看清问题:规划 Agent 现在拿到的是什么

看 main 分支原版的 `_build_planner_query`(294–326 行),它把三个**字符串**拼进提示词:

```python
**景点信息:**
{attractions}

**天气信息:**
{weather}

**酒店信息:**
{hotels}
```

`attractions` 是景点 Agent 的**最终回复文本**——格式不稳定、没有结构化的坐标列表。而要求区的第 3、5 条(318–321 行)写着:

```
3. 考虑景点之间的距离和交通方式
5. 景点的经纬度坐标要真实准确
```

这就是问题的全貌:**你要求 LLM 做"考虑真实距离"和"坐标真实准确"这两件它根本做不到的事。** 它不知道任意两个景点的距离(训练数据里没有精确值),却被迫编造坐标——这正是模块三之前"假坐标"的根源之一。修法不是换更强的模型,而是**把数据喂进去**。

## 2.2 地理编码:`maps_geo`,地址与坐标的翻译官

`geocode`(amap_service.py 188–217 行,TODO 桩在 212–213 行)封装的是 `maps_geo` 工具,调用协议和第 15 课完全一样:

```python
result = self.mcp_tool.run({
    "action": "call_tool",
    "tool_name": "maps_geo",
    "arguments": arguments   # {"address": address, 可选 "city": city}
})
```

**地理编码(Geocoding)= 地址 → 结构化坐标。** 典型返回(以你侦察到的为准):

```json
{
  "status": "1",
  "geocodes": [
    {
      "formatted_address": "北京市东城区景山前街4号",
      "country": "中国",
      "city": "北京市",
      "location": "116.397026,39.918056"
    }
  ]
}
```

和 POI 搜索的分工,记住一句话:**有精确地址用 `maps_geo`,只有模糊名称用 `maps_text_search`。** "北京市东城区景山前街4号"适合 geo;"故宫博物院"这种 POI 名字,`text_search` 给的结果更准(还附带 POI id)。反过来,由坐标查地址叫逆地理编码(maps_regeocode),高德 MCP 工具列表里也有(启动日志 `amap_service.py:40-45` 打印的前 5 个工具里就能看到),本课用不到,知道即可。

解析写法与第 15 课同构:判 `status` → 取 `geocodes[0]` → **注意查不到地址时 `geocodes` 是空数组**(这不算错误,`status` 仍是 "1")→ 拆 `location` 字符串转 float。函数签名约定返回 `Optional[Location]`,查不到就返回 `None`,诚实降级。

## 2.3 路线规划:三种工具怎么选

`plan_route`(122–186 行)的桩里其实已经埋好了选择题,`tool_map`(145–149 行):

```python
tool_map = {
    "walking": "maps_direction_walking_by_address",
    "driving": "maps_direction_driving_by_address",
    "transit": "maps_direction_transit_integrated_by_address"
}

tool_name = tool_map.get(route_type, "maps_direction_walking_by_address")
```

三个要点:

1. **`by_address` 后缀**:这类工具直接收地址字符串,服务端内部先做地理编码再规划——所以它其实"包含"了 2.2 的能力,你可以把它当成"地址版通勤计算器"。代价是地址不够准时静默失败,所以关键场景可以先 `geocode` 校验地址有效性再查路线。
2. **transit 的参数更挑剔**:160–164 行给公共交通多塞了 `origin_city` / `destination_city`——公交跨市和市内是不同引擎,缺城市参数是 transit 报错的头号原因。
3. **静默兜底藏了坑**:151 行 `tool_map.get(route_type, "maps_direction_walking_by_address")`——传个 `"fly"` 不会报错,而是悄悄变成步行。对内部调用这可以接受,但你应该让上游只传合法值:`RouteRequest.route_type`(`schemas.py:49`)的 description 虽然写了三种,却没有校验。可以在 schema 层加校验(选做)。

**怎么选?别自己猜,用户的 `TripRequest.transportation`(`schemas.py:16`)已经说了**——它是个自由字符串(如"公共交通"),做个映射:

```python
def _route_type_for(self, transportation: str) -> str:
    """把用户的交通偏好映射为高德路线工具类型"""
    if "步行" in transportation:
        return "walking"
    if "自驾" in transportation or "打车" in transportation or "开车" in transportation:
        return "driving"
    return "transit"   # "公共交通"等默认走公交
```

## 2.4 haversine:先算直线,再查路线

N 个景点两两组合是 N(N−1)/2 对——10 个景点就是 45 次路线查询,配额和延迟都吃不消。标准解法:**用便宜的直线距离做粗筛,只对"疑似接近"的对子发起真实路线查询。**

球面两点直线距离用 haversine 公式(把地球当半径 R≈6371km 的球):

```
a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlon/2)
d = 2R·asin(√a)
```

写成 Python,建议放在 `amap_service.py` 底部作为模块级函数(它不依赖任何实例状态):

```python
from math import radians, sin, cos, asin, sqrt

def haversine_m(lon1: float, lat1: float, lon2: float, lat2: float) -> float:
    """两点间大圆距离(米)。注意:直线距离,不是路程!"""
    r = 6371000.0
    lon1, lat1, lon2, lat2 = map(radians, (lon1, lat1, lon2, lat2))
    a = sin((lat2 - lat1) / 2) ** 2 + cos(lat1) * cos(lat2) * sin((lon2 - lon1) / 2) ** 2
    return 2 * r * asin(sqrt(a))
```

两个使用纪律:

- **直线距离 ≠ 路程**,北京老城里实际走路通常是直线的 1.2–1.5 倍。它只适合做"这两点是否值得查一次真实路线"的粗筛,和给用户展示的兜底估计(要标注"直线距离");
- 阈值取多少看城市尺度:市内游可以设"直线超过 8 公里的对子不排同一天",具体数值你对比实验时自己调。

## 2.5 注入规划 Agent:改造 `_build_planner_query`

现在把三块积木拼起来。目标:在 `plan_trip` 里拿到**结构化的景点列表**,算出两两通勤表,塞进规划查询。

**第一步:拿结构化景点。** 景点 Agent 的输出是自由文本,别去解析它——直接用第 15 课的成果,服务层直调:

```python
from ..services.amap_service import get_amap_service

amap = get_amap_service()
pois = amap.search_poi(keywords, request.city)   # List[POIInfo],带真实坐标
```

这里用上了第 1 课埋的伏笔("双通道"设计):**Agent 适合模糊决策,直连服务适合确定性查询**——拿坐标列表是确定性需求,走服务层。

**第二步:算通勤表**(放在 `trip_planner_agent.py`,模块级或类方法):

```python
def _compute_transit_section(self, city: str, pois, route_type: str,
                             max_pois: int = 8, max_straight_m: float = 8000) -> str:
    """计算景点两两通勤,返回注入提示词的文本段"""
    from ..services.amap_service import haversine_m
    amap = get_amap_service()
    pois = pois[:max_pois]          # 控制查询规模
    lines = []
    for i in range(len(pois)):
        for j in range(i + 1, len(pois)):
            a, b = pois[i], pois[j]
            straight = haversine_m(a.location.longitude, a.location.latitude,
                                   b.location.longitude, b.location.latitude)
            if straight > max_straight_m:
                lines.append(f"- {a.name} ↔ {b.name}:直线约{straight/1000:.1f}公里(太远,不建议安排在同一天)")
                continue
            route = amap.plan_route(a.address or a.name, b.address or b.name,
                                    origin_city=city, destination_city=city,
                                    route_type=route_type)
            if route:
                lines.append(f"- {a.name} ↔ {b.name}:{route['duration'] // 60}分钟,"
                             f"{route['distance'] / 1000:.1f}公里({route_type})")
            else:
                lines.append(f"- {a.name} ↔ {b.name}:直线约{straight/1000:.1f}公里(路线查询失败,仅参考)")
    return "\n".join(lines) if lines else "(无景点对,跳过)"
```

**第三步:接进异步主流程。** `plan_route` 是同步的,你的 `plan_trip` 已是 async——按第 12 课的方法丢进线程:

```python
transit_section = await asyncio.to_thread(
    self._compute_transit_section, request.city, pois,
    self._route_type_for(request.transportation)
)
```

**第四步:改 `_build_planner_query`**(294–326 行),加一段真实数据区,并把"要求"里的愿望升级成指令:

```python
**景点间通勤时间(真实数据,必须作为安排顺序的依据):**
{transit_section}
```

同时在要求列表里加一条:

```
6. 同一天的景点必须从"通勤时间短"的相邻景点中选择,严禁同一天安排通勤超过90分钟的两个景点
```

注意:重复查询(同一城市多跑几次实验)会大量浪费配额——第 18 课你会用 30 分钟 TTL 缓存把这层开销直接抹掉,本课先忍着,或把 `max_pois` 调小。

## 2.6 动手实验:补完两个桩 + 绕路程度对比(本课核心任务)

### 任务 A:补全 `geocode` 与 `plan_route` 的解析

3. 验证:`/docs` 里 `POST /api/map/route` 用默认 body(阜通东大街 → 上地十街,`schemas.py:43-49` 的示例)拿真实距离时长;再用 `geocode` 的结果反查一个地址确认坐标正确。

### 任务 B:数据驱动 vs 凭感觉——同一城市对比实验

1. 选一座熟悉的城市,2 天行程、`max_pois=6~8`;
2. **对照组**:临时注释掉注入的通勤数据区(保留原始 `_build_planner_query` 行为),生成 3 次行程,保存结果;
3. **实验组**:打开注入,同样生成 3 次;
4. **量化"绕路程度"**:对每次结果的每一天,把景点按输出顺序连线,计算相邻景点直线距离之和;再用"贪心最近邻排序"(每次选离当前点最近的未访问景点)算出该天可达的近似最优顺序,比值 = 实际顺序距离和 ÷ 贪心距离和,**比值越接近 1 越不绕路**。10 行以内的脚本就能算(坐标就在结果 JSON 里);
5. 把 6 份结果的比值、代表性案例(如"第 2 天从西边的颐和园跳到东边的 CBD 再跳回去")写进 `docs/lesson16-route-compare.md`,并写下你的结论。

### 常见卡点

- **"transit 工具一直报参数错误?"** —— 99% 是没传 `origin_city` / `destination_city`(160–164 行的逻辑只在 transit 分支必传);另外同城 transit 的地址必须在同一城市,先拿 `geocode` 确认两点确实同城。
- **"两个很近的景点查步行路线却返回空?"** —— 高德部分起终点过近或不可达(如公园内部)会返回空路线,走"直线距离兜底 + 标注仅参考"的诚实降级,别编数字。
- **"注入后 token 暴涨、规划变慢?"** —— 正常:通勤表增加了输入量。用 `max_pois` 和直线阈值控制规模;第 18 课的缓存会把重复实验的成本削掉大半。另一个提醒:这段查询在 `asyncio.to_thread` 里跑,不要图省事直接写在协程里阻塞事件循环。
