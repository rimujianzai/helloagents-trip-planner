## 1.1 启动入口:run.py 与 uvicorn

后端的启动入口只有 16 行,值得全文精读:

```python
# backend/run.py(全文)
"""启动脚本"""

import uvicorn
from app.config import get_settings

if __name__ == "__main__":
    settings = get_settings()

    uvicorn.run(
        "app.api.main:app",
        host=settings.host,
        port=settings.port,
        reload=True,
        log_level=settings.log_level.lower()
    )
```

两个细节:

1. `uvicorn.run` 的第一个参数是**导入字符串** `"app.api.main:app"` 而不是直接传 app 对象——因为 `reload=True` 的热重载要靠子进程重新 import,传对象就失效了。
2. `host` / `port` / `log_level` 全部来自 `Settings`——它们从哪来,就是本课 1.2 节的主题。

等价的手动命令(README 第 96 行的写法)是:

```bash
cd backend
uvicorn app.api.main:app --reload --host 0.0.0.0 --port 8000
```

顺带看一眼根目录的 `start.bat`:第 2 行 `chcp 65001` 把控制台切成 UTF-8(否则后端日志里的中文和 emoji 全是乱码),第 11 行直接用 `venv\Scripts\python.exe -m uvicorn ...` 起后端、第 14 行 `npm run dev` 起前端。它只是把本课的手工步骤串了起来——**你至少要会手工版,脚本版才有意义**。

## 1.2 配置体系:一份 .env 的三重加载

打开 `backend/app/config.py`(111 行)。同一个 `.env`,其实在三个地方被读了三遍:

```python
# config.py:9-16
# 加载环境变量
# 首先尝试加载当前目录的.env
load_dotenv()

# 然后尝试加载HelloAgents的.env(如果存在)
helloagents_env = Path(__file__).parent.parent.parent.parent / "HelloAgents" / ".env"
if helloagents_env.exists():
    load_dotenv(helloagents_env, override=False)  # 不覆盖已有的环境变量
```

```python
# config.py:49-52
    class Config:
        env_file = ".env"
        case_sensitive = False
        extra = "ignore"  # 忽略额外的环境变量
```

| 次序 | 谁在读 | 读哪里 | 说明 |
|---|---|---|---|
| 第 1 次 | `load_dotenv()`(11 行) | **当前工作目录**的 `.env` | 即你运行命令时所在的目录 |
| 第 1.5 次 | 16 行 | 仓库**上一级**的 `HelloAgents/.env`(若存在) | 教程仓库的遗留逻辑;`override=False` 表示不覆盖已加载的值 |
| 第 2 次 | pydantic-settings(50 行 `env_file=".env"`) | 当前工作目录的 `.env` | `Settings()` 实例化时再读一遍 |

实际的取值优先级是:**真实的系统环境变量 > `.env` 文件 > 类里的默认值**(`load_dotenv` 默认不覆盖已存在的变量,pydantic-settings 也是环境变量优先)。由此得出一个重要纪律:

> **必须 `cd backend` 之后再启动**。`load_dotenv()` 与 `env_file=".env"` 都是相对当前目录找文件——在仓库根目录启动,`.env` 就找不到了。这也是第 2 课"常见卡点"里 `ModuleNotFoundError: No module named 'app'` 的同源原因:导入路径同样以当前目录为基准。

至于 16 行那个外部 `HelloAgents/.env`:它指向**仓库目录的上一级**里名为 `HelloAgents` 的文件夹(通常是你装 Hello-Agents 教程代码的目录)。存在就借它的配置,不存在就跳过——这解释了为什么有些同学"明明没配 .env 也能跑":配置被隔壁教程仓库泄漏进来了。理解这个行为,排查配置问题时才不会见鬼。

## 1.3 Settings 字段导览:两套 LLM 变量名之谜

`Settings` 类(19–56 行)逐字段过一遍,重点看它和 `backend/.env.example` 的对应关系:

| Settings 字段(行号) | .env 里的变量 | 谁在用 |
|---|---|---|
| `host` / `port`(28-29) | `HOST` / `PORT`(.env.example 16-17) | `run.py` 启动监听 |
| `cors_origins`(32) | `CORS_ORIGINS`(.env.example 20) | `main.py:23` CORS 白名单 |
| `amap_api_key`(35) | `AMAP_API_KEY`(.env.example 30) | MCPTool 传给高德 MCP 服务 |
| `unsplash_access_key`(38) | `UNSPLASH_ACCESS_KEY` | `unsplash_service.py` 景点配图 |
| `openai_api_key` / `openai_base_url` / `openai_model`(42-44) | (没有直接对应的 .env 变量) | **只是带默认值的占位字段** |
| `log_level`(47) | `LOG_LEVEL` | `run.py` |

注意 32 行的写法:

```python
# config.py:31-32
    # CORS配置 - 使用字符串,在代码中分割
    cors_origins: str = "http://localhost:5173,http://localhost:3000,http://127.0.0.1:5173,http://127.0.0.1:3000"
```

明明语义是列表,却声明成字符串,再由 `get_cors_origins_list()`(54–56 行)手动 `split(',')`。这是在绕 pydantic-settings 对 `List[str]` 字段的解析坑(它会要求 .env 里写 JSON 数组格式)。作者的取舍未必最优,但**见到"字符串字段 + 手动 split"你应该立刻猜到是环境变量解析在作怪**。

真正的谜题在 LLM 配置:`backend/.env.example` 第 2–13 行写的是另一套名字——

```
# backend/.env.example(节选)
LLM_MODEL_ID=deepseek-flash        # 4 行
LLM_API_KEY=YOUR_API_KEY           # 7 行
LLM_BASE_URL=https://api.deepseek.com/v1   # 10 行
LLM_TIMEOUT=60                     # 13 行
```

而 `Settings` 里只有 `openai_api_key` 等三个占位字段。`LLM_API_KEY` 去哪了?答案在 `validate_config`(77–80 行)和 `print_config`(103–105 行)——它们**不走 Settings,直接用 `os.getenv` 读**:

```python
# config.py:77-80
    # HelloAgentsLLM会自动从LLM_API_KEY读取,不强制要求OPENAI_API_KEY
    llm_api_key = os.getenv("LLM_API_KEY") or os.getenv("OPENAI_API_KEY")
    if not llm_api_key:
        warnings.append("LLM_API_KEY或OPENAI_API_KEY未配置,LLM功能可能无法使用")
```

原因:`HelloAgentsLLM` 框架类**自己从环境变量读配置**(`llm_service.py:22-24` 的注释明说了),完全绕过本项目的 Settings 对象。所以 `LLM_*` 变量不必定义在 `Settings` 里,只要躺在进程环境里就行。这条"绕开 Settings 的暗道"是理解第 5 课的前提,先记住结论:**改 LLM 配置 = 改环境变量,改完必须重启进程**。

## 1.4 启动自检:validate_config 与 print_config

FastAPI 应用创建后(`main.py:12-18`,注意 16–17 行注册了 `docs_url="/docs"` 和 `redoc_url="/redoc"`),`@app.on_event("startup")`(35 行)注册的启动事件会做两件事(46–52 行):调 `print_config()` 打印配置摘要,再调 `validate_config()` 校验。两者的严格程度完全不同:

```python
# config.py:74-84(节选)
    if not settings.amap_api_key:
        errors.append("AMAP_API_KEY未配置")       # 进 errors → 直接抛异常

    llm_api_key = os.getenv("LLM_API_KEY") or os.getenv("OPENAI_API_KEY")
    if not llm_api_key:
        warnings.append("LLM_API_KEY或OPENAI_API_KEY未配置,...")   # 只警告
```

- **AMAP_API_KEY 留空 → `errors` → `ValueError` → 启动失败**(82–84 行抛出,`main.py:49-52` 重新 raise,uvicorn 直接退出)。这叫 **fail fast**:问题在启动一刻暴露,好。
- **LLM key 缺失 → 只有 warning,照常启动**——坏消息被推迟到第一次调规划时才爆。两种设计各有道理,第 14 课讨论"诚实报错"时再回来对照。

另外,启动时你可能看到 `DeprecationWarning: on_event is deprecated...`——`main.py:35` 和 60 行用的 `@app.on_event` 写法已被 FastAPI 弃用,应改用 lifespan。功能不受影响,**第 21 课把它列进 Bug 狩猎清单**。

## 1.5 前端配置与跨域真相:两个都配了,只有一个在干活

前端侧有三个环境变量(`frontend/.env.example`):

```
# frontend/.env.example
VITE_API_BASE_URL=http://localhost:8000      # 2 行:后端地址
VITE_AMAP_WEB_KEY=YOUR_AMAP_WEB_KEY          # 5 行:高德 Web 服务 Key
VITE_AMAP_WEB_JS_KEY=YOUR_AMAP_WEB_JS_KEY    # 7 行:高德 JS API Key(浏览器画地图用)
```

Vite 只会把 `VITE_` 前缀的变量暴露给 `import.meta.env`(这是安全设计:防止你把密钥误暴露给浏览器,但注意 `VITE_` 前缀本身就能被前端读到,**别把后端密钥放前端 .env**)。

再看 `frontend/vite.config.ts` 里的开发服务器配置:

```ts
// vite.config.ts:13-21
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:8000',
        changeOrigin: true
      }
    }
  }
```

教科书式配置,对吧?**但它在本项目里根本没被用上。** 回看 `api.ts:4`:`baseURL` 是绝对地址 `http://localhost:8000`——Axios 直接请求后端,请求压根不经过 Vite 开发服务器,proxy 自然无法转发。验证方法:打开 DevTools 的 Network 面板,请求 URL 是 `http://localhost:8000/api/trip/plan` 而不是 `http://localhost:5173/api/...`。

于是真正的跨域方案是后端的 CORS(`main.py:21-27`):

```python
# main.py:21-27
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.get_cors_origins_list(),   # 白名单来自 config.py:32
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

CORS 与开发代理是**同一个问题的两种解法**:代理让请求"同源"(绕过检查),CORS 让后端"放行"(通过检查)。本项目两边都写了,但绝对 baseURL 决定了只有 CORS 在干活。还有一处漏网之鱼:`Result.vue:435` 硬编码了一个 `http://localhost:8000` 的 fetch 调图片接口——同属"该治理的绝对地址",第 24 课一起算账。

> 顺带巩固第 2 课的伏笔:`AMAP_WEB_KEY`(给后端 MCP 查数据用)和 `AMAP_WEB_JS_KEY`(给浏览器画地图用)是**两个不同的高德 Key**,对应第 1 课"两个高德"的分工。申请入口都在 lbs.amap.com,Key 类型别选错。

## 2. 动手实验:从零跑通 + 故意配错 + /docs 实战(本课核心任务)

### 实验一:从零跑通前后端

1. **后端虚拟环境**(Windows Git Bash / PowerShell 命令分列,取其一):

```bash
cd backend
python -m venv venv
```

   安装时对照 `requirements.txt` 认脸:第 2 行 `hello-agents[protocols]>=0.2.4,<=0.2.9` 是框架本体(第 5 课去源码里找它);`fastmcp` + `uv`(24-25 行)是 MCP 栈(第 10 课);`loguru`(21 行)已装但全项目还没用(第 19 课的活);`httpx` + `aiohttp`(11-12 行)是 HTTP 客户端(第 5、17 课用)。

### 实验二:故意配错,观察报错链路(先备份 .env)

| 情形 | 做法 | 预期观察 |
|---|---|---|
| A. 高德 key 留空 | `AMAP_API_KEY=` | 启动**当场失败**:`ValueError`,错误信息来自 `config.py:83` 的拼接 |
| B. 高德 key 填假值 | `AMAP_API_KEY=FAKE123` | 启动正常;第一次真正规划时才在高德/MCP 侧报错(具体报错样式以你实际观察为准,记进笔记) |
| C. LLM key 留空 | 注释掉 `LLM_API_KEY` | 仅有 warning(`config.py:87-89`),启动照常;调规划时才失败 |

每改一次都要**重启后端进程**再观察(改动 .env 不会触发热重载)。做完恢复备份。

### 实验三:/docs 手工调用

1. 打开 `http://localhost:8000/docs` → `POST /api/trip/plan` → "Try it out";
2. 请求体粘贴 `schemas.py:22-33` 的 example(城市北京、3 天)→ "Execute";

### 完成标准

- [ ] 两个终端分别跑着后端(8000)与前端(5173),`http://localhost:8000/` 返回 JSON;

### 常见卡点

- **"`ModuleNotFoundError: No module named 'app'`?"** —— 启动目录不对。`app` 包在 `backend/` 下,必须在 `backend/` 目录里运行;`.env` 的查找同样依赖这个目录(1.2 节)。
- **"改了 .env 不生效?"** —— 两连问:重启进程了吗?改的是 `backend/.env` 吗(pydantic-settings 找的是当前目录那份)?另外注意环境变量优先于 .env 文件,如果你曾在系统里 export 过同名变量,文件里的值会被压制。
- **"前端控制台一片 CORS 红字?"** —— 依次检查:后端是否真的在 8000;`config.py:32` 白名单是否包含你的前端源(改了 `cors_origins` 记得重启);确认你走的是绝对 baseURL(与 Vite 代理无关,1.5 节)。
- **"pip install 到一半报编译错误?"** —— 优先确认 Python 版本是 3.10+;`uv` 与 `aiohttp` 在老版本 Python 上容易翻车。虚拟环境的意义就在这里:搞砸了删掉 `venv/` 重来,不污染系统。
